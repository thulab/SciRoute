# Bounded asynchronous result fetch

The registration socket accepts one explicit versioned request:

```json
{"kind":"result_fetch","version":1,"path":"<absolute published immutable result path>"}
```

Requests retain the existing big-endian uint32 JSON framing and 1MiB request bound. A success response is a framed JSON header `{"ok":true,"kind":"result_fetch","version":1,"size":N}` followed by exactly N raw Arrow IPC bytes. Before handoff, errors retain the existing `ok/code/phase/message` frame; after a partial transfer, EOF is failure and callers discard incomplete bytes. Fetch does not execute or regenerate a query, and a failed fetch never retires a shared publication. Registration-response failure rollback is unchanged.

Each new socket authenticates the peer using the existing credential policy. The path must belong to this mount and contain an exact immutable result identifier. `FuseTypedQueryBridge::acquire_exact` resolves the registered route and checks current source permissions/owner admission and the existing metadata fees, using a fresh request budget. A published locator is not permission evidence. Existing version/head validation remains in that admission path. Permission and namespace gates end before network delivery, as on an authorized FUSE open. The producer execution lease is not transferred to the sender.

One reservation is acquired before public query-task submission and retained through authorization, send, or failure. At most 16 fetch reservations exist; there is no unbounded waiting delivery queue. A full/stopped sender rejects admission with a structured error. Authorization uses the public query scheduler without native format execution resources. On handoff the query execution slot is released normally, while the bounded delivery reservation, connection/completion guard and immutable result handle remain pinned. Store resident-byte accounting therefore lasts until the last owner releases the result.

The daemon setting `query.result_fetch.sender_threads` selects one (default) or two poll reactors, each with its own queue and nonblocking wakeup pipe. Reservations remain globally capped at 16; each reservation has one fixed shard. Cancellation wakes that shard. A scoped read-only slice pins the existing immutable payload and its accounting state. `sendmsg` offers remaining length prefix, JSON header and payload as iovecs, with a combined per-round budget of at most 64KiB and a 4KiB maximum header. It advances offsets across all framing boundaries after a partial write. There is no temporary payload vector; ordinary socket sending still involves kernel copying. Kernel socket buffers remain bounded by the host socket configuration. Successful handoff configures the socket nonblocking, suppresses SIGPIPE, handles partial writes and applies the existing three-second no-progress timeout. Continued progress can exceed three seconds overall. Cancellation/EOF/timeout/stop release only the affected open and delivery reservation. Stop wakes and joins the reactor before draining request completion guards and retiring registries.

The probe client uses the same single asyncio loop and eight existing query coroutines. Each query remains `catalog -> typed1 -> await fetch1 -> owned1 -> typed2 -> await fetch2 -> owned2`; there is no client executor or intra-query parallelism. It bounds payload admission to 64MiB and reads in 64KiB chunks before Arrow BufferReader decoding and owned values/masks. Complete query timing ends after owned output; profile harvesting and full oracle hashes stay outside. Fetch admission is an additional scheduler task but does not create a catalog/typed profile record. Client fetch intervals include scheduler/authentication/transport/event-loop waits and do not measure simultaneous server sends or physical CPU parallelism.

Opt-in segmented timing uses `IOTDBFS_RESULT_FETCH_TRACE_JSONL`. It buffers at most 8192 records, with paths capped at 4096 bytes; oversized diagnostic paths drop the record without limiting the request API. A transfer records accept/transport/frame-read, public-task submission/start, fresh admission, sender enqueue/dequeue, first/all successful send returns, and sender-owned cleanup. At most 64 send-call spans include wall start/end, requested bytes, returned bytes and errno; truncation is counted. Thread CPU is sampled only when timing is enabled. The measured CPU includes the small internal steady-clock sampling overhead. The buffer is written after stop joins senders and drains requests, followed by a summary with explicit drop count. Diagnostics do not append ordinary query profile rows.

`first_send_ns` and `last_send_ns` are timestamps taken after successful syscall returns; `last_send_ns` denotes all bytes accepted by the kernel, not client receipt or owned-copy completion. A server thread can be descheduled before taking its return timestamp, so that timestamp can even follow client receipt. `cleanup_ns` on successful handoff follows release of sender-owned references; scheduler captures or bridge cache references can still exist. For a failure before handoff it is the handler error-tail timestamp, not a sender cleanup or final budget-refund timestamp. Send-call wall-interval overlap measures overlapping calls, including possible descheduling, and does not prove physical CPU parallelism. Primary performance probes disable this detailed tracing and collect diagnostic runs separately.
