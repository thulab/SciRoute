# mac 分支跨平台合并后续工作计划

## 1. 计划目的

本计划整理《评估 mac 分支跨平台合并》线程中尚未完成的工作，作为后续实施、验证和发布的执行清单。

平台范围和当前证据见[平台支持矩阵](../knowledge/support-matrix.md)。

目标是维护一条以当前 `master` 为基线的主线：Linux 和 macOS 原生运行，Windows 第一阶段通过 WSL2/Linux 用户态运行；只有在明确采用 WinFsp 或 Dokany 后，才启动 Windows 原生挂载适配。

## 2. 当前基线

已确认或已完成的内容：

- `origin/mac-version` 相对当时的 `master` 主要独有内容是 `mac/schema.xml`；该文件本身不能代表完整的 macOS 支持。
- 平台抽象、暂存文件、ecCodes 可执行路径发现、CMake 平台分支和 macOS schema 安装已加入当前工作区。
- IoTDB 客户端、连接池、FUSE 文件语义、缓存、Web 安全和 SQL 边界已完成一轮修复。
- 配置驱动元数据已形成独立模块，当前采用有界 typed JSON 保留动态字段；扩展配置、投影、查询评估、缓存和 schema 能力已有单元测试。
- Linux 构建通过；当前测试清单已达到 295 项并通过，包含元数据扩展、平台暂存文件、inode schema、崩溃恢复和环境预检相关测试。
- Windows 原生构建会明确拒绝并提示使用 WSL2；这属于已定义的产品边界，不等于 Windows 原生挂载已完成。
- 工作区仍有未提交的代码、测试和文档改动，需完成审查、整理和由用户执行的 Git 提交。

## 3. 尚未完成事项

### P0：跨平台实机验收

#### macOS

- 使用 AppleClang、macFUSE、ecCodes、Boost 和 IoTDB C++ 客户端完成干净环境构建。
- 安装并检查 `mac/schema.xml`，确认 Finder 属性声明与程序实际属性名称一致。
- 验证挂载、卸载、重复挂载、异常退出后的清理、文件复制和 Finder 浏览。
- 验证权限、属主、纳秒级时间戳、截断、随机写、追加、稀疏写、共享句柄和历史版本。
- 明确并验收 xattr 语义：派生 GRIB 属性只读；用户扩展属性是否持久化必须先定案。若不支持写入，接口必须返回明确错误码，不能伪造成功。
- 明确并验收 `statfs` 容量语义：使用真实配额/使用量，或明确声明能力不可用；不能继续使用固定估算值。

#### 主流 Linux

- 在至少一个发行版之外再验证一套常见环境（例如 Ubuntu 与麒麟/其他目标发行版）。
- 使用真实 IoTDB 和 FUSE 完成读写、重命名、覆盖、重挂、权限和历史版本回归。
- 对新建数据库未就绪、连接失败、SchemaRegion 尚未可用等启动错误进行可重复验证。

#### WSL2

- 验证 WSL2 中的构建、ecCodes 资源路径、临时文件、Web 服务和基础挂载。
- 记录 WSL 文件系统路径与 `/mnt/*` 路径下的差异、FUSE 权限要求和已知限制。

### P0：真实 IoTDB/FUSE 端到端验收

- 建立隔离 IoTDB 实例和独立测试数据库，测试完成后确认进程、端口、挂载点和凭据均清理。
- 覆盖普通文件和 GRIB 文件两种模式：创建、追加、偏移覆盖、截断、稀疏写、共享读写句柄、flush/fsync、重命名、覆盖重命名、删除和重挂。
- 每个写入场景都必须在卸载并重新挂载后校验内容、长度、SHA-256、历史版本和索引，避免只验证内存缓存。
- 覆盖连接池大小 1 和默认大小，验证结果集跨客户端生命周期、并发读写及失败重试。
- 对 IoTDB 写入失败、索引失败、元数据写入失败和中断恢复进行故障注入；确认未完成版本不会被发布为最新版本。
- 完成跨文件查询、跨版本查询、语义检索和 GRIB 开关开启/关闭的端到端回归。

### P1：macOS 专用属性和容量能力定案

在实现前记录设计决定：

1. 用户 xattr 是否进入 IoTDB 持久化模型；若进入，定义大小上限、删除语义、版本关联和迁移策略。
2. `statfs` 报告的是配置配额、逻辑容量还是数据库实际可用空间；定义未配置时的错误或能力标识。
3. 是否注册 `setattr_x`、`fsetattr_x`、`statfs_x`；每个回调都必须与当前 FUSE 文件语义一致，尤其是 size 变化必须真正执行截断/扩展。

输出物：一份设计决定记录、对应单元测试、macOS 实机验收记录和用户手册更新。

### P1：配置驱动扩展元数据收尾

- 审查当前未提交的元数据模块和测试，确认公共接口、配置文件路径、类型转换、错误处理和线程安全契约稳定。
- 将 `resources/metadata.properties` 的示例、字段命名规则、可查询字段、xattr 映射和重载行为写入部署文档。
- 验证旧 inode 行、缺失 `metadata` 列、非法 JSON、超限文档和配置热重载失败时的行为。
- 决定动态字段是否继续只存 JSON；若后续需要 IoTDB 索引，基于 `MetadataQueryEvaluator` seam 单独设计索引，而不是直接改变现有 inode 表。
- 增加至少一项真实 IoTDB 验收：动态字段写入、重挂读取、xattr/Web 展示和查询结果一致。

### P1：崩溃恢复与发布一致性

- 定义暂存文件、IoTDB OBJECT、inode 行和索引之间的提交顺序及持久化成功含义。
- 模拟进程在写入、索引、元数据、重命名和删除各阶段退出，验证重启后的可见版本和孤儿对象处理。
- 提供可重复的恢复/清理工具或运维步骤，并把失败状态记录到文档。

### P2：mulversion 分表设计（独立决策项）

当前不直接移植 `mulversion`。若重新采用独立 `grib_meta` 表，必须先批准以下方案：

- 以文件版本作为关联键，保存当前全部 GRIB 字段和持久化格式身份；格式不能每次由扩展名重新推断。
- 设计停写迁移：备份、建表、复制全部历史版本、逐项校验、切换、失败恢复；不使用运行时双读双写掩盖不一致。
- 同步修改挂载、扩展属性、`CrossFileClient`、`SemanticGrepClient`、删除和重命名路径。
- 覆盖连接池大小 1，避免持有第一张表结果集时嵌套租借第二个连接。
- 验证跨扩展名重命名、删除、历史版本、迁移中断和重试。

若暂不批准，应继续保留当前 inode 内的 JSON/固定字段方案，并在发布说明中明确“独立元数据表和历史迁移未提供”。

### P2：Windows 原生路线评估

- 第一阶段继续支持 WSL2，不编写伪兼容层。
- 如果产品要求 Windows 原生挂载，先完成 WinFsp 与 Dokany 的接口、部署、授权、性能和维护成本比较。
- 选定方案后再抽象 FUSE 回调依赖、文件句柄、目录枚举、锁、xattr 和错误码；单独建立 Windows CI/实机矩阵。

### P2：性能与静态分析

- 在固定数据集、机器配置和并发参数下，建立 Linux/macOS/WSL 的基准，分别记录吞吐、延迟、内存、暂存空间和 IoTDB 请求数。
- 对连接池大小、缓存预算、元数据缓存、索引批量阈值和大文件随机写做对比。
- 在可用环境运行 ASan、UBSan、TSan 或等价工具；记录未运行工具及原因，不能以普通 CTest 替代。

## 4. 推荐执行顺序

1. 冻结当前工作区，审查未提交改动，确认配置驱动元数据的公共 API 和文档。
2. 在 Linux 隔离 IoTDB/FUSE 环境重跑端到端矩阵，保留重挂后的证据。
3. 完成 macOS 实机验收，并据结果决定 xattr、容量和专用回调的最终语义。
4. 完成麒麟或另一目标 Linux 发行版、WSL2 的构建和基础运行验收。
5. 运行崩溃恢复和故障注入测试，关闭所有 P0/P1 数据一致性缺口。
6. 对 `mulversion` 分表和 Windows 原生挂载分别作产品决策；未批准的方向保持延期状态。
7. 更新用户手册、发布说明、支持矩阵和已知限制。
8. 由用户检查差异并执行 Git 提交、合并或推送；代理不执行 Git 写操作。

## 5. 验收门槛

只有同时满足以下条件，才能将“跨平台合并后续工作”标记为完成：

- Linux、macOS 和 WSL2 的目标构建与基础运行通过，并有环境、依赖和版本记录。
- 真实 IoTDB/FUSE 端到端场景在卸载重挂后全部通过，包含失败和重试路径。
- macOS xattr、容量、专用回调语义已有明确结论和实机证据。
- 动态元数据配置、持久化、投影、Web/xattr 展示和查询行为一致。
- 崩溃恢复、历史版本、重命名、删除和索引一致性通过故障注入验收。
- 支持矩阵、安装说明、已知限制和回滚步骤已更新。
- 当前工作区改动完成审查，Git 提交与合并由用户确认并执行。

## 6. 风险与跟踪原则

- `mac/schema.xml` 只能视为资源文件，不能作为完整 macOS 支持证明。
- Linux 测试全绿不能推导 macOS、WSL2、麒麟或 Windows 原生行为正确。
- 旧分支的固定容量、吞掉 xattr 写入、整文件内存暂存和单线程参数不得直接复用。
- 性能结论必须绑定数据集、并发、机器和 IoTDB 配置；不得从功能测试通过推导“无性能退化”。
- 任何涉及新数据表、迁移、格式身份或 Windows 原生后端的设计，在实施前先形成可评审方案和验收用例。
