# 4.3／4.4 的增量复测范围

2026-10-31，核对飞书文档 revision 1163。此文件只界定复测范围，不改写旧实测数据。

不要求重跑全部历史优化列或全部三路查询矩阵。旧“静态索引、已发布语料上的查询”结果仍回答原问题；新增维护能力不会使旧 raw timing 自动失效。原 4.3 的 N/C/S 与 4.4 的历史选择不要混入不同工作负载的维护成本后仍称为同一测量。

可以优先在相同沙箱中添加 `FS-index incremental v2` 查询列，复用相同 raw、case、oracle、版本选择与完整 owned 输出。新建独立维护目录并按原科学版本顺序导入；原 raw、SQLite v1、IoTDB namespace/head 均不改动。准备成本和查询成本分开，新增的文件复制、完整发布校验、SQLite FULL 提交、第一次 reader 刷新和 checkpoint 另列，不把 v2 构造成本冒充旧 v1 build 时间。

优先代表点（两格式）：N8/V1、独立 N128/V1、N512 全域/窄域；N8/V8 与 V32 的 Latest、首代、All。代表点可先检查新旧 FS-index 是否有实质差异，再扩到正文实际使用的查询点。不重跑已经拒绝的中间优化、训练或未用于主张的登记组。已有 query-only warmup/repetition 规则保持，同一 case 的多用途只采样一次。

有两项不能直接替换：

1. v2 当前发布 profile 要求**所有**单元 4096 个值。4.3 的 S1/S2 非命中单元为 384²/768²，不在该 profile 内。保留 v1 对这些组的结果及其实现名称；若论文要声称 v2 完整覆盖 S 扩展，需要先扩展发布校验与对应测试，再补测，不能静默跳过不支持单元。
2. 新 FS-index 数字不能除以旧 IoTDB-FS 数字后宣称“同期 R”。保留历史配对 R。若要更新论文正式三路比值，只在用于该主张的代表点/正文点补同轮三路，或明确标识异时描述性比较。不能先用结果是否漂亮决定哪些点补测。

资源也必须实际核对：旧两节限制客户端、FS/FUSE 与 DataNode 共用 CPU2/3 两核父配额，query≤2GiB，DataNode 内存另计。M1 第一轮曾仅限制客户端/FS/FUSE，已保留为失败诊断；修订正式轮将 DataNode 纳入共享两核，但保留当前 JVM 内存配置，不重启数据库。维护轨迹仍是新的工作负载，**不是旧 FM1 查询表的直接重测**。仅称“2 核/2G”不足以证明两次实验环境相同。

当前新增三路 M1 的必要性独立于查询矩阵复测：原表没有完整“发布＋增量更新＋后续查询＋显式收尾”的三路轨迹。因此 M1 三路需重新采集；不能将旧查询时间简单加到新 FS-index 维护时间上。M2 并发更新、M3 超缓存/网络边界不由 M1 自动完成。
