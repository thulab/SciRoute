# IoTDB-FS 训练路径：成本边界与有区分力的场景

> 文档整理：标为“服务器归档”的引用按本次清单不再作为 Git 文档保留，查验路径见 [文档归档说明](../README.md#服务器归档)。

后续已完成[prepared执行与buffer转换消融](../reports/public-training-execution-cost-20260930.md)：同轮对照的暖缓存wall为6.759→5.287秒。本文保留该次优化之前的分析/实验口径。

日期：2026-09-30。本文复核现有实验与代码，没有运行新实验，也没有修改运行时。问题从“怎样继续降低单次 wall time”转向“哪些成本是架构的代价，以及哪些真实工作负载能用收益覆盖这些代价”。

## 1. 先明确比较对象与证据边界

当前 A 是本地原始、未压缩 Arrow stream，通过 mmap、message/row 索引、进程内有界 RecordBatch 缓存按需切窗，再由 NumPy 标准化。B 是相同源数据摄取到 IoTDB-FS 后，通过 prepared snapshot/view、训练查询、共享 decoded cache、结果 IPC 和只读 FUSE 路径交给训练器。它不是只有“底层文件系统”一个变量的实验。

两条路径都按需生成窗口；A 没有预先存储所有重叠训练窗口。因此“避免保存重叠窗口”不是当前 B 相对 A 的独占收益。B 提供统一的版本绑定、视图、覆盖验证、来源追踪、预算和多实验共享机制，而 A 使用受控实验的 manifest 与 reader。讨论这些机制的价值时，应分别核对双方提供的语义。

最新数据取自客户端批量转换消融（服务器归档：`docs/public-training-client-conversion-20260930.md`），只选优化后的 `batch` 组：两模型、两次重复，共四次冷、四次暖运行。每次 50 steps、实际 51 次训练 fetch、102 个样本，batch=2、L=96、H=24、370 通道，标准 HF RandomSampler。精确源版本、轨迹、值/mask 与 loss 已核验一致。缓存 1 GiB/16,384 entries、四路读取，冷暖均无驱逐或重复 decode。

| 指标，整轮均值 | 本地 A | B 冷 decoded cache | B 暖 decoded cache |
|---|---:|---:|---:|
| train wall | 2.125 s | 7.305 s | 6.562 s |
| 训练 fetch | 1.104 s | 6.148 s | 5.388 s |
| wall 减去 fetch | 1.021 s | 1.157 s | 1.174 s |
| B payload 读取调用 | — | 120 | 0 |
| B payload 返回字节 | — | 109,117,440 B | 0 |
| B fragment decode | — | 6,660 | 0 |

暖缓存 wall 差距为 **4.437 s**，其中 fetch 差距 **4.284 s，约占 96.6%**。但不能把 B 的 5.388 s fetch 全算成额外成本：A 也要执行取样、复制和标准化。`wall-fetch` 也不是纯 GPU 计算时间，包含 Trainer 与调度等工作。

“冷”只清空 daemon 的 decoded cache，没有清空 OS/IoTDB 缓存。冷暖 wall 相差 0.743 s，是此配置下的条件对照，不是磁盘读取成本或数据库延迟下限。暖缓存没有 payload 读取，不代表没有 inode/layout 等元数据访问。

另一个口径限制是 A 的 reader 初始化/message-offset 扫描发生在 `train_wall` 之前，B 首次 lazy prepare 在第一次 fetch 内。后续生命周期实验必须对称报告 setup、首样本、首 epoch 与后续 epoch。现有数字不应称为双方完整启动到训练结束的总成本，也只有短程、少量重复证据。

## 2. 当前暖缓存的时间花在哪里

以下通过同步客户端阶段与其内部服务端阶段分解，不重复累加父子计时；总和为 6.562 s。[派生数值与原始字段](../results/arrow-client-conversion-20260930/architecture-cost-breakdown.json)可复核计算。

| 阶段 | 整轮时间 | 解释 |
|---|---:|---|
| 首次 prepared 注册 | 0.080 s | 一次性成本，长训练可摊薄 |
| window prefetch | 0.552 s | 此时无 payload I/O，仍有需求映射、cache key、lease、预算与 provider 工作 |
| 其余 window execute | 1.300 s | 规划/assembler 创建、组窗、变换与收尾 |
| IPC 编码 | 0.526 s | 将已生成的窗口转换为 flat Arrow IPC |
| 发布前源授权 | 0.437 s | source inode 与父目录权限检查 |
| 结果发布 | 0.201 s | 内容身份、结果存储和准入等；未单独证明全部是哈希 |
| 客户端 stat | 0.453 s | FUSE/授权等整条 stat 路径，不能全称为权限时间 |
| IPC open/mmap/read | 0.152 s | 客户端读取结果 |
| 客户端验证和数组转换 | 1.566 s | 验证 0.420 s、数组转换 1.128 s，剩余为调用/收尾 |
| 其他 fetch 残差 | 0.121 s | 控制通信、release、客户端收尾等，非独立插桩阶段 |
| fetch 以外 | 1.174 s | Trainer、计算及其他工作 |

`window_execute` 总计 1.852 s，内部包含 planner 创建 0.366 s、assembler 创建 0.095 s、标准化 0.529 s。fingerprint 0.219 s 和 view 验证 0.290 s 是内部嵌套计时，不能额外加到总时间上。空载调度 admission 与 wait 合计约 0.000314 s，当前不能把调度器说成主瓶颈。

训练值本身为 102×120×370×4 = **18,115,200 B**；加一字节 mask 为 **22,644,000 B**。IPC 为 **85,791,200 B**，分别约 4.74 倍和 3.79 倍。该比例描述当前 flat schema 和元数据等共同造成的体积，不代表 Arrow 格式必须这样膨胀，也尚未按字段精确分解全部增量。控制请求已降为每轮 139,538 B，原来的大声明不再是当前主要问题。

## 3. 哪些是保留架构后必然存在的成本

“固有”应限定为**机制不能完全消失**，而不是现有某项秒数无法降低。普通文件系统也有权限、页缓存和内存搬运，额外成本来自实现这些能力的位置、频率和边界。

### 3.1 独立查询服务的进程边界

A 的暖路径可在训练进程内直接访问已映射的数据。B 的新请求要到达 daemon、取得共享状态并让客户端消费结果。保留外部查询服务，就必须有请求通知、结果可见性和生命周期协调。跨机器使用时还有网络传输与往返；本机也有相应进程/内核边界。

可以合批、长连接、共享内存、预取和流水线，减少每样本承担的次数或隐藏在计算之后，但不能同时要求服务独立、结果由它产生，又假定训练器获得结果完全没有协调成本。隐藏 wall time 也不等于消除了 CPU、带宽和内存占用。

### 3.2 未命中时的数据库访问路径

保留 IoTDB 作为存储后端，缺失数据要经过存储定位、会话/请求、服务端处理和返回；它不能直接等同于本地暖 mmap 指针访问。范围与字节成本都可能存在，批量与并行可摊薄但不抹去工作本身。

已有[read-shape 测量](../reports/public-training-read-shape-profile-20260929.md)中，同为 1 MiB 时 1 range 约 11.18 ms、64 ranges 约 17.17 ms；64 KiB 时分别约 4.12/10.68 ms。这些是会话、SQL/RPC 和返回转换等综合实测，不是磁盘 seek 或网络 RTT 的单独测量，更不是优化后的理论下限。当前暖路径已消除了 payload 读取，所以继续缩小 tile 或增加读并行不能消除暖缓存的 4.437 s 差距。

### 3.3 一致性、权限和共享资源协调

精确 source/version、snapshot 身份、权限隔离、缓存 lease 与全局预算都需要状态和校验。若要求跨挂载的权限变化及时生效，就需要刷新或可靠失效机制；不能无条件永久缓存授权。

但“每个 minibatch 重算完整 fingerprint”“每条新 route 重新查所有父目录”不是这些语义的必然实现。已验证不可变对象可以摊销验证，授权可在明确有效期/失效语义下共享。普通文件的已打开 fd/mmap 在 chmod 后的访问语义，与每个新 query 重新授权也不完全相同；减少检查须明确选择语义，而不是因为 A 没做就直接删除。

### 3.4 不同视图最终输出的工作

共享原始 fragment 不等于共享所有实验的最终 tensor。不同通道、窗口长度、标准化统计产生不同输出；采用当前 dense、独立拥有内存的结果契约，就仍要形成每份结果。A 同样要进行相应切窗、变换和 tensor 准备。

B 额外的多次表示转换并非都必需。若改为引用基础共享内存、延迟变换或直接输出 tensor，就能改变复制与计算位置，但也要重新处理所有权、租约、mask、取消与预算。这是接口和架构变化，不是证明现在所有复制都“无法优化”。

## 4. 哪些仍有优化空间，以及属于哪一层

| 当前现象 | 判断 | 可能的改进与边界 |
|---|---|---|
| 每轮 planner/assembler 创建约 0.461 s，含重复 snapshot/view 验证 | 实现重复工作 | 对 prepared 内部不可变对象编译/验证一次；保留可变公开入口的防篡改验证 |
| 暖 prefetch 0.552 s，无 payload I/O | 命中路径的管理成本 | 合并需求、复用绑定和 key、批量 lease；共享预算与取消语义仍需保持 |
| 标准化 0.529 s | 算法/实现成本，不是数据库代价 | 当前逐样本建 statistics map、逐元素按 field/ordinal 查 map；可预编译按通道排列的统计并批量计算，保持 double 中间值、finite 与 mask 语义 |
| IPC 85.79 MB、编码 0.526 s、客户端转换/验证 1.566 s | 主要由当前前端协议与实现决定 | 更贴近 tensor 的布局、减少结构性冗余、批量 builder/转换、固定声明只验证一次；不可直接丢弃 provenance 或改变 null/NaN 语义 |
| 结果发布 0.201 s | 部分源于不可变内容路径契约 | 目前对完整 IPC 做内容身份计算与准入；可研究融合编码/哈希、减少遍历。代码将 vector 移交给 payload，不能误称发布总会再复制一整份 |
| socket 授权 0.437 s，另有 stat 0.453 s | 有必要检查，也有重复路径 | 按主体、源集合/版本和权限 generation 复用；stat 总时间不能全部当成可省授权时间 |
| 同步每 minibatch 请求并完整物化 IPC | 当前架构选择 | 更大服务侧预取组、流水线或专用训练传输；不必改变模型 optimizer batch，但会增加在途结果与调度复杂度 |
| 首次注册 0.080 s | 一次性成本 | 继续复用已足够重要；仅此项不值得作为当前主攻方向 |
| 历史 1,024-entry 驱逐、串行读波次 | 已证明可改的实现限制 | 当前配置已消除驱逐并采用四路读取，不能继续拿旧问题解释当前结果 |

IPC/FUSE 的现行链路是“窗口数组→flat IPC→不可变结果对象→FUSE 映射→PyArrow→dense NumPy”。普通源文件已经 mmap，不需要为每个窗口发布一个新文件。结果本身支持 mmap 只消除了部分访问限制，不能追溯消除上游编码与下游列到 dense tensor 的转换。

因此应区分：**保留当前 IPC/FUSE 入口时难以完全消除的成本，不等于 IoTDB-FS 存储模型固有的成本。** 更换为共享内存/tensor 接口可以重新分配这些成本，但会改变产品契约，不能当成零成本调参方案。

现有阶段计时也不足以给出“最多还能省 X 秒”的承诺。各项包含必要工作，A 已有自身对应成本；未来并行还会改变关键路径，不能把各阶段时间机械相减得到优化后 wall 下限。

## 5. 哪些场景值得寻找区分

### 5.1 首选：多实验共享昂贵解码

真正有希望的收益是：多个实验消费同一精确源版本，输入长度、目标、通道或标准化不同，但访问到的基础解码单元在缓存驻留期间重叠。独立 reader 本来会重复做的解压/解析，由 daemon 只做一次，可能用这份节省覆盖服务与输出成本。

当前实现的共享范围是**同一个挂载 daemon 的 QueryRuntime**。多个训练进程可以共享，多个 daemon/backend 实例或主机不会自动共享 decoded cache；同内容换路径也不自动去重。窗口输出与变换仍逐实验产生。

最值得测量的是压缩 Arrow 或其他解码昂贵的原始格式，而不是当前未压缩 Electricity。当前 Arrow 压缩路径缓存整块 batch/field 的 Float32 leaf buffer，包含其嵌套 rows/channels；它不是只解压所选窗口的 tile，且批量 provider 会回退到 scalar loader。小 granule 无法突破压缩单元边界。共享解压可能收益更大，也可能受单 buffer 与临时内存限制，必须同时记录。

关键强对照是本地 **R1-sharing**。普通文件系统完全可以支持共享解码服务；若只击败每进程私有解码缓存，结论应是“统一共享解码服务优于该私有 reader 配置”，不能证明该能力只能由 IoTDB-FS 提供。

### 5.2 次选：真实超内存、宽变量、稀疏需求

当实际活跃工作集超过总内存预算，少数时间范围/通道查询是否减少真实 I/O 与解码，才有决定性意义。需要 native 格式访问单元、压缩方式、选择性与 reuse distance 共同满足条件。

不能假设 mmap 的 A 读取一个 RecordBatch 就把整个 batch 从磁盘复制到私有内存。未压缩数据可按页访问，共享 OS page cache；16 KiB tile 甚至可能比实际需要的文件页更粗。当前 reader 的 `decoded_bytes`/`cache_bytes` 是 `batch.nbytes` 的逻辑统计，不是物理磁盘流量、解压量或新增私有内存。因此该场景必须测 page faults、真实磁盘/网络字节和 PSS，不能用逻辑 decode counters 宣布优势。

“大文件”也不自动等于超内存。应使用真实语料与明确双方总资源预算，避免只限制 A 或只给 B 额外服务器缓存。比较远端部署时须控制存储拓扑，不能把 B 的网络访问与 A 的本地访问差异都算到查询算法上。

### 5.3 自然跨文件、多个版本与多视图的生命周期

此场景的区分可能是少做每实验预处理、统一缺失/覆盖语义、可复现版本与来源、减少派生数据维护，而不是每个窗口更快。应使用本来就分 shard 的数据和真实更新，不人为拆 Electricity 制造跨文件。

本地有索引的 reader 也能跨文件切窗；连续 memmap（R2）也是强替代方案。只有实际需要保存每视图结果的对照，才可以声称节省了这些物化副本；不能把本来按需切窗的 R1/R2 也算成必然保存所有窗口。必须计入双方转换/摄取、建索引、首次准备、更新、历史版本/派生对象空间与清理成本，观察多少实验/epoch 后摊销。

### 5.4 多实验预算和尾延迟隔离

共享缓存、single-flight、每实验并发/在途预算可能减少重复生产与内存失控，保护小实验在大实验旁边的供给延迟。这里应考察总吞吐、每实验 p95 等待、公平性、峰值物理内存和失败率，而非只看单任务平均值。

目前没有该并发场景的实测胜出证据。并发也可能导致共享缓存污染、锁竞争和预算等待；必须与有总预算控制的本地共享 reader 比较。

## 6. 哪些论据目前不能成立

- **“多个实验就会节省 N 份源数据内存”。** A 的 mmap 文件页本就可共享；不能累加 RSS 或 Arrow nbytes 推算重复物理驻留。压缩后私有解码缓冲才是更明确的验证对象。
- **“GRIB 表现好，所以 Arrow 只需调整 tile 大小”。** GRIB message 的自然解码成本/单位与未压缩 Arrow 不同；当前 Arrow 暖路径主要成本已经移到窗口服务与结果消费。原 GRIB 对照也未必经过同样的训练前端。
- **“模型变大后 IoTDB-FS 就有性能优势”。** 大模型可能摊薄比例，异步供给可能隐藏等待，但并不证明节省了数据路径资源；当前同步 collator 并不能自动实现重叠。
- **“预取合批应当一定提高随机训练命中率”。** 必须看字节复用距离和实际采样；不同实验应保留独立种子，不为了命中而强制同步相同窗口。
- **“6.562 s 是不可突破的架构下限”。** 计时中仍有明显实现重复与协议转换，没有测得这样的下限。

## 7. 建议的验证顺序

保留当前未压缩、单实验、暖缓存作为负对照：它显示本地 mmap 的自然优势，并约束关于通用加速的表述。不要通过放大模型计算或人为放慢 A 让这条结果消失。

优先补足归因对照，再选择真实场景：

1. **R4 plain IoTDB-FS + 相同本地 reader**：隔离数据库/FUSE 存储路径与 typed 训练服务。R4 是诊断，不能取代主要 A。
2. **本地 R1-sharing**：与同 daemon Q2 对比私有/共享解码；若要再区分训练查询框架与后端，也可设计相同训练查询接本地文件 source 的对照，但这是尚未实现的方案。
3. 在真实压缩数据上运行 1/2/4 个独立实验，固定总预算、数据版本与每实验轨迹，比较共享解码收益及尾延迟；先做 loader-only，再做 Trainer，避免 GPU 争用掩盖供给差异。
4. 如果收益确实由解码/内存而非样本同步产生，再扩大到自然超内存与多 shard 场景。压缩、投影比例、工作集/内存比与实验数分别控制，不混成一次不可归因的大对比。

预算需覆盖客户端、daemon、IoTDB 服务、decoded/encoded cache、在途结果和 OS page cache；共享页按 PSS/共享映射核算。报告首次准备、首 epoch、稳态 epoch、总 CPU、实际 I/O、解码次数、字节命中和尾延迟。现有[基线计划](../deliverables/public-training-baseline-plan.md)已规定这些强对照与资源口径，应沿用。

判断标准是：**省下的重复解码、真实 I/O 和每实验准备/物化成本，能否超过新增的服务协调、结果生成与传输成本。** 当前 Electricity 单实验没有提供足够的前者，所以 A 快是合理结果；最值得验证的差异是昂贵基础解码在多个真实实验间的复用，而非继续追求对暖 mmap 的全面胜出。
