# Arrow：布局收益与 IoTDB-FS 系统收益的对照结果

本轮证明了 **128 点派生布局对两个存储路径均有效，但尚未观察到同布局下 IoTDB 后端或生产 typed 路径优于普通 FS**。布局缩小了 IoTDB 取数路径的绝对劣势，不能据此声称 IoTDB-FS 系统已经取得端到端优势。

## 实验控制

详见 [预先记录的方法](../deliverables/arrow-layout-system-control-experiment.md)。生产 C++ 二进制保持不变，SHA256 `ac32a6b3b6f70ffc0d129268c6914c0bd61e32e70cb22850888e6e0faf63ab33`。真实原始文件两行/batch；128 点 step-major 为一行/batch；全部 Arrow IPC 未压缩。原始 source SHA256 `536c3c72afb04f09daadf860ef021719bb4f90515c10a6710bd35d78de18fa0f`，精确版本 `1790670177863`。

主对照共用同一实验读取器、decoder、1 GiB 按字节缓存、组装、标准化及连续 input/target/mask 输出。普通 FS 为 mmap，另有普通 read 敏感性对照；IoTDB 使用原始 IPC message 范围 helper。生产 typed 路径另列，包含其额外契约和不同的服务端缓存位置。

固定原 50-step 轨迹：51 请求、102 窗口、370 通道、L96/H24；5 轮，每轮 1 冷＋3 暖，交错运行、不并发。冷仅清空应用 decoded cache，未清理 OS/IoTDB 缓存；原始 offset 索引、hash 校验和 reader setup 单列。每次请求计时后逐位校验标准化 Float32 和 mask。

完成 **280 条轨迹观察、14,280 次窗口请求**，全部校验通过；所有暖遍实际 payload 读取和解码为零，typed 暖遍 prepare 为零。原始/派生读取器、prepared client 与构建测试 15 项，加上统计校验测试 6 项，合计 **21 项 Python 测试通过**。本轮未修改生产代码，也未重跑模型训练。

## 主 2×2：相同读取器和未压缩编码

时间包含取数、解码、缓存、组装、标准化和连续输出，单位秒/完整轨迹。`均值 [最小, 最大]` 以五个独立重复计；暖遍先在每轮内部取三遍均值。

| 存储路径 | 原始布局：冷 | 128 点 step-major：冷 | 原始：暖 | 128 点：暖 |
|---|---:|---:|---:|---:|
| 普通 FS mmap | 0.207 [0.173, 0.259] | 0.078 [0.075, 0.081] | 0.101 [0.089, 0.119] | 0.022 [0.019, 0.023] |
| IoTDB 范围 helper | 1.797 [1.762, 1.863] | 0.587 [0.568, 0.599] | 0.107 [0.086, 0.127] | 0.022 [0.021, 0.023] |

按同一轮次配对计算：

| 成本变化 | 冷轨迹结果 |
|---|---:|
| FS 内部布局加速 | 2.651× |
| IoTDB 内部布局加速 | 3.061× |
| 原始布局的 IoTDB−FS 额外时间 | 1.591s |
| 派生布局的 IoTDB−FS 额外时间 | 0.509s |
| 布局改变带来的额外时间差缩减 | 1.082s |

速度比是五轮配对比值的均值，并非表中均值直接相除。派生布局下 IoTDB 范围路径仍约为同布局 FS 的 **7.52 倍耗时**。它减少了约 1.08 秒的绝对额外时间，但没有消除剩余约 0.51 秒。

暖路径两侧约 0.022 秒，都只访问各自进程内的数组缓存；这不是 IoTDB 存储比 FS 更快的证据。原始与派生的暖差别则来自内存访问与窗口组装方式，不能归因于减少了后端 I/O。

普通 read 对照：原始冷 0.220 秒、派生冷 0.078 秒；对应 mmap 为 0.207/0.078 秒。结论不依赖仅选用某一种本地读取 API。

## 分块、batch 组织和转置分别贡献什么

| 物理布局（全部 none） | FS mmap 冷 s | IoTDB 冷 s | FS mmap 暖 s | IoTDB 暖 s |
|---|---:|---:|---:|---:|
| 真实原始：两行/batch | 0.207 | 1.797 | 0.101 | 0.107 |
| channel-major 8192：一行/batch | 0.183 | 1.510 | 0.100 | 0.090 |
| channel-major 128 | 0.089 | 0.604 | 0.029 | 0.029 |
| step-major 128 | 0.078 | 0.587 | 0.022 | 0.022 |

- 原始→CM8192 同时减少一次解码/读取所覆盖的行数，不能把这部分称为时间块长变化。
- CM8192→CM128 保持通道优先组织，冷阶段的大部分改善来自缩小时间块。
- CM128→SM128 冷阶段的额外改善较小，暖阶段仍有组装和内存局部性收益。低 I/O 时，布局可以通过改变 CPU 访问方式继续影响性能。

同一实验读取器在两种布局下触及的 IPC 字节一致：原始 **121.260 MB**、派生 **31.176 MB**，下降 **74.3%**；物理解码 batch 从 5 个大 batch 变为 164 个小 batch。IoTDB 范围调用从 15 增至 50 次，小块节省字节仍超过增加调用的成本。FS 原始为 5 次范围访问，派生为 91 次；IoTDB 一次 API 可承载多个不连续范围，不能将两侧 API 次数直接当作磁盘 I/O 次数。

mmap 的 `io_seconds` 只覆盖建立 buffer 视图，页访问可能落在 decode/assemble 阶段；不能把 mmap 的近零该项计时解释为没有内存或页访问成本。本轮也不测物理磁盘读字节。

## 生产 typed 路径：布局收益仍被附加处理抵消

| 生产路径 | 冷总时间 s | 其中首次 prepare s | 冷时间减首次 prepare s | 同一上下文暖总时间 s |
|---|---:|---:|---:|---:|
| 原始 | 4.517 | 0.100 | 4.417 | 3.713 |
| 128 点 step-major | 8.326 | 3.531 | 4.796 | 4.285 |

扣除首次准备也未取得端到端改善；这一列只是同一次测量的分解，不是另一种冷启动实验。生产路径的原始 payload 为 109.117 MB，少于实验 helper 的 121.260 MB，因为原始 typed 查询按 tile 选择数据，而 helper 解码整个 IPC batch。两者不同的范围模型也是实现差异，不能直接相减后全部归因于 IPC。

| 阶段 | 原始暖 s | 128 点暖 s |
|---|---:|---:|
| planner 创建 | 0.002 | 0.002 |
| prefetch／缓存需求处理 | 0.324 | 0.503 |
| 窗口组装 | 0.101 | 0.042 |
| 服务端授权 | 0.418 | 0.628 |
| IPC 编码 | 0.637 | 0.549 |
| 结果发布 | 0.203 | 0.232 |
| 客户端 FUSE stat | 0.448 | 0.644 |
| 客户端 IPC 读取 | 0.166 | 0.180 |
| 客户端结果校验与数组转换 | 0.984 | 1.111 |

128 点窗口组装确实减少，但缓存需求处理、授权、stat 和客户端处理的增量将它抵消。输出 IPC 从 **85.79 MB** 增至 **98.20 MB**，与更细块的 provenance 数量增加有关。初始 coverage prepare 从约 **0.031 秒增至 1.819 秒**，module prepare 从 **0.022 秒增至 0.884 秒**。

这组生产对照证明的是当前实现的成本分布，不是 IoTDB 的不可消除固有开销。FS/实验 helper 只返回训练数组，typed 还提供授权、来源说明、版本绑定、服务端共享缓存和结果协议；生产与 helper 的总差值不能视作单一系统组件的因果成本。

## 启动、构建与存储成本

本轮原始源外部索引准备 **0.853 秒**，其中扫描约 **0.356 秒**、hash 约 **0.497 秒**，在轨迹计时外。reader setup 另列于 JSON；原始 FS mmap 约 0.0003 秒、原始 IoTDB helper 约 0.024 秒；128 点分别约 0.001/0.015 秒。typed reader 构造约 0.028/0.165 秒，冷轨迹内另含首次 prepare。

派生文件复用既有已验证版本，不重新构建。128 点未压缩 artifact 为 **208.299 MB**，原始为 **207.613 MB**；保留两者意味着额外存储约 208 MB。既有构建清单记录 source decode 2.445 秒、构建 0.801 秒、全值校验 2.092 秒；源解码可由多个候选共享。该清单的 ingestion_seconds=0 是已存在文件的复用，不是零成本新摄取，不能据此计算完整生命周期的精确回本点。

## 对论文假设的含义

1. **布局收益成立，而且并非 IoTDB-FS 独有**：两个后端在相同读取器下均获益。
2. **布局可缩小后端额外成本**：这里绝对差从 1.59 秒降至 0.51 秒，但同布局 FS 仍更快。
3. **单客户端、已建立索引、全部工作集可缓存的负载，没有证明 IoTDB-FS 系统优势**。暖客户端缓存也不证明数据库读取优势。
4. 下一步可检验多实验重叠读取、跨文件元数据筛选等真实需求，但应继续允许 FS 使用合理索引和缓存。当前结果不足以支持“所有科学格式子集查询均优于 FS”，也不能反推出“Arrow 无布局优化空间”。

本轮是固定 50-step 轨迹回放，不是新一轮模型训练、完整 epoch 或并发服务测试。五轮只报告描述统计，不声称小幅差异具有统计显著性。
