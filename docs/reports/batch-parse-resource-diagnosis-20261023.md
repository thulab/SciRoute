# 批量解析 A/B：既有资源记录复核

日期：2026-10-23。只分析上一轮保存的记录，不追加实验、实时采样、服务重启或资源配置变更。对应[完整查询验收](batch-parse-ab-20261022.md)。

**结论：实验栈在虚拟机内的 CPU2/3 分区约束有证据支持，但不能称物理双核独占或性能环境固定。N128 末轮两臂变慢时，其他30个 vCPU 的忙度从3.98%升至74.37%，这是明确的环境变化证据；尚不能确定是频率、共享缓存／内存竞争还是其他执行成本变化。数据库活动可能干扰部分轮次，但不足以解释末轮最大退化。**

## 2. 双核隔离是否有效

保存环境明确记录 KVM、32个 vCPU。所有核验快照中，parent的partition=root、effective/exclusive CPUs=2–3、cpu.max=200000/100000；query和DataNode在member子组，共用两核容量。所属进程的可用亲和性／cgroup观测未见越界；所记录的外部ConfigNode允许集合为0–1,4–31。正式查询资源包络未见quota限流或OOM。

因此可以确认**保存观测范围内，guest分区约束按设计生效**，不能把本轮问题简单归结为taskset未生效。但仍有以下边界：

- 两核配额规定容量上限，不保证最低CPU服务、固定频率或各进程公平份额；数据库仍与查询进程共享这两个vCPU。
- 当前是允许内部负载均衡的root分区；不是内核的isolated分区。未记录IRQ／全部内核线程／所有外部root任务的实际执行CPU轨迹。
- 运行时快照主要验证进程允许集合，不能替代每个TID的实际调度轨迹；快照读取也不是原子的。
- guest vCPU约束不能证明宿主物理核绑核、无超售、物理SMT关系，或缓存／内存带宽独占。guest展示的单线程拓扑不足以推出宿主拓扑。

依据：[Linux cgroup v2 cpuset分区定义](https://docs.kernel.org/admin-guide/cgroup-v2.html)。实现核对位置：experiments/cross_version/resource_limited/resources.py 的创建／验证逻辑，以及 experiments/fixed_matrix/run.py 的 validate_sample。

## 3. 两臂 CPU 同步增长：末轮的直接证据

N128末轮按AB执行，A开始于北京时间00:33:43，B开始于00:35:02。下表查询与包络项是正式查询中位数，忙度／idle是各配置完整块级窗口。

| 指标 | A | B |
| --- | ---: | ---: |
| IoTDB-FS 完整T（ms） | 7.579 | 19.813 |
| IoTDB-FS d／q（ms） | 3.688／4.037 | 9.896／9.774 |
| FS-index 完整T（ms） | 1.008 | 3.194 |
| FS-index d／q（ms） | 0.572／0.431 | 2.119／1.070 |
| IoTDB-FS 查询组CPU包络（ms） | 13.197 | 32.102 |
| FS-index 查询组CPU包络（ms） | 6.161 | 15.048 |
| IoTDB-FS 客户端self CPU包络（ms） | 7.422 | 15.405 |
| FS-index 客户端self CPU包络（ms） | 6.203 | 14.406 |
| IoTDB-FS 查询组CPU PSI some增量（ms） | 0.0465 | 0.0870 |
| guest全部32 vCPU忙度 | 5.63% | 72.15% |
| guest其他30 vCPU忙度，扣除2/3 | 3.98% | 74.37% |
| 实验vCPU2／3 idle | 69.89%／67.03% | 45.95%／75.17% |

**支持的判断：**两臂的客户端CPU和查询组CPU都增长，多个阶段同步变慢；末轮B与实验分区外的大量guest活动重合。故环境共同因素应优先考虑，不能将完整T增加全部归因于B的解析改动。N128第1轮也出现其他30 vCPU忙度6.40%→31.83%、两臂T都增加约26.6%的现象。

**不支持的判断：**末轮两个实验vCPU没有持续饱和，查询组PSI小、配额限流为0，不符合“只是排队等不到CPU”的单一解释。CPU累计时间增大说明整个资源包络在执行状态消耗更多时间；可能来自较低有效执行速度、缓存／内存停顿或额外执行工作。它并不证明指令数增加，也不能仅靠此项反推CPU降频。保存记录没有周期／指令／缓存未命中或物理频率证据，不能分配各机制的因果贡献。

其他轮次不呈统一关系：例如N128第3轮B的外部guest忙度更低而T仍略高。因此不能把全部轮次归为一个后台高负载事件，也不能用末轮相关性证明B没有额外成本。AB／BA／BA／AB只能减少部分顺序偏差，不能消除短时非平稳负载。

## 4. 频率与虚拟化调度

全部16个配置环境中的cpu2/3 cpufreq频率、governor等字段不可用。lscpu中的2.10 GHz是型号描述，不是该时段实际运行频率。**现有记录不能确认或排除频率变化。**

16个查询块的guest总CPU、cpu2、cpu3 steal增量均为0；但包括准备／等待等阶段的完整周期记录并非全为0：N8全guest累计增加25 ticks，cpu2/3增加2／1 ticks；N128全guest增加72 ticks，cpu2/3增加3／3 ticks。100 Hz下，两实验vCPU分别合计30／60 ms。这说明计数器有变化，不能说全程没有虚拟化调度损失；也没有证据将这些全生命周期损失归到末轮查询。

依据：[Linux /proc/stat与steal定义](https://docs.kernel.org/filesystems/proc.html)。查询块steal为0不等于宿主资源隔离，也不排除共享缓存、内存或功耗／频率影响。

## 5. 数据库后台活动

| N128配置 | IoTDB查询包络内database组CPU中位（ms） | 查询组CPU PSI中位（ms） | 与查询块重叠的周期database组CPU占用（100%=一vCPU） |
| --- | ---: | ---: | --- |
| 第2轮A，较慢 | 13.089 | 2.386 | 约34.9%–42.2% |
| 第2轮B，较快 | 0.062 | 0.743 | 约0.9%–1.5% |
| 第4轮B，最大退化 | 1.216 | 0.087 | 约3.0%–9.6% |

上述CPU来自database cgroup的cpu.stat，不能当作DataNode单进程的精细CPU统计。数据库和查询共享vCPU，第2轮A存在数据库组CPU活动与查询等待升高同时发生的证据，**与后台工作争用相符**。但SDK调用计数中位为0不是“数据库完全空闲”，也不能据组CPU区分GC、压缩、心跳或其他维护任务。当前所核验资源记录没有对应线程级CPU／GC事件归因。

末轮B的数据库组CPU和查询PSI远低于第2轮A，且两个vCPU仍有明显idle；现有记录不支持“DataNode持续占满两核造成末轮2.6倍／3.2倍退化”。周期窗口较粗，仍不能排除短时后台干扰。

## 6. 结论和处置

| 假设 | 既有证据结论 |
| --- | --- |
| 双核设置失效、查询进程逃逸 | 已保存的分区和所属进程观测不支持；无法证明全部内核／外部瞬时执行都被排除 |
| 配额耗尽或持续CPU排队 | 未见正式包络限流；末轮PSI小且实验核有idle，不支持其为主要解释 |
| 实验分区外guest活动变化 | 有直接证据；末轮其他30个guest vCPU忙度显著升高，属于最强共同环境线索；未识别具体任务 |
| 频率／缓存／内存资源竞争 | 机制上可能，现有记录缺少区分证据，不能确诊 |
| 数据库后台任务 | 部分轮次有活动／等待相关证据；具体任务未知，不足解释末轮最大退化 |
| B代码本身导致全部变慢 | 不能成立为已有结论；同样不能排除B有较小的自身成本 |

保留A主线和B归档，不因本轮资源分析重新采纳B。此前回退是按完整T验收门槛的保守处置，不是代码因果判决。后续实验框架应区分“资源上限固定”和“环境性能稳定”，不能再将当前两核限制描述为物理资源完全隔离。本轮未执行任何新增实验或采样。
