## 口径与实现

- 三个原始 HDF5 尺寸、相同 `/T` 点选择、精确源版本、源文件副本和 HDF5 1.14.4 动态库；逐文件 SHA 与原 resident 数据对齐。
- 三个原生组：FS-scan、FS-index 重开、FS-index 句柄缓存。三轮轮转组顺序和 Q=1/10/100 顺序；每源每组先记录一条首请求和两条暖身请求。
- 共 **81 个独立测量会话、2,997 次测量查询，加 81 次首请求/暖身**；不筛除慢样本。`sessions.csv` 保留逐轮直接计时，`summary.json` 同时保留均值、中位数、范围和各轮原始值。
- 句柄缓存上限 8 个 file/dataset 会话；本负载每轮实际打开 3 个。每条查询重新查 SQLite 目录、检查不可变源 stat 身份，再调用一次 `H5Dread`，产生独立持有的值和 mask。未添加应用层值/结果缓存。
- 缓存键包含物理路径、逻辑路径、精确版本、dataset。实际 HDF5 默认 chunk cache 为每 dataset **1,048,576 B、521 slots、w0=0.75**；每轮三个 dataset，共 3 MiB 配置上限，不含其他库元数据。
- 缓存在组/轮内保留；首次打开计入首请求。三种源的缓存组首请求均值为 **1.006 / 0.802 / 0.775 ms**，不称冷缓存读。每轮最终关闭三个句柄另计 **0.197 / 0.195 / 0.636 ms**；暖查询表不摊入这笔结束服务成本。
- Q=1 是暖态单次请求，不能解释为“创建服务、构建索引、读取一次、销毁服务”的总成本。每条请求都重新执行原生值读取，但 HDF5 可以在已有 chunk cache 中满足它。

## 隔离与验证

沿用 CPUs 2–3 的共享两核总配额、查询 2 GiB、swap=0；DataNode 位于同一两核父配额中，其 28/4 GiB heap/direct 设置单独记录。ConfigNode 继续在配额外。服务器、DataNode PID/start ticks、配置/JAR 哈希和库身份与原 resident campaign 一致。没有重置服务、清空缓存或重发语料。

本地与服务器均通过目录/句柄缓存 **10 项单元测试**。真实数据资格检查覆盖三个源的两个坐标，验证命中时读取新坐标、返回数组独立持有以及容量为 1 时的淘汰/关闭。正式审计核对全部值与 mask 摘要、每查询一次原生读取、每查询目录检查、缓存命中/打开/关闭计数和完整会话时钟。

独立审计核验 **65 个资源快照、18 个安静窗口门禁、258 个冻结 Python 源文件**。监督进程正常结束（316.353 s）；**500 个现存 DataNode 线程**的原亲和性、原 cgroup、同一进程身份及原配置/JAR 均通过恢复核验。三轮各打开 3 个句柄、339 次命中、最终全部关闭。

唯一正式采集 `handles-formal-001` 完整通过；未删除或重跑查询记录。首次后处理尝试因归档旧导出模块缺少 helper 导入失败，随后改用自包含 `handles-export-002.py` 完成审计。该修正未改变采集源码、记录或统计口径。
