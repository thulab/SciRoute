# 三路径增量维护生命周期 M1

日期：2026-10-31。**状态：M1 修订正式轮完成，54条轨迹、1,296次发布、31,968次正式查询全部验证通过，资源已恢复；M2/M3未执行。** 本文件与 [运行协议](../../experiments/maintenance_lifecycle/README.md)、[4.3/4.4 复测范围](../deliverables/fs-index-query-refresh-scope-20261031.md) 配套。原论文和飞书历史数字未被覆盖。

## 目标与可比性

补齐 FS-scan、增量维护 FS-index 与 IoTDB-FS 在同一发布/查询轨迹上的成本：8 个初始逻辑文件、每文件4单元、16次新版本发布、每次更新后 q=1/10/100 查询。GRIB/HDF5 两格式，三轮，54轨迹。各次查询都返回两份64×64 Float32＋uint8 mask，40,960B。q≥10含10%每路径v1，其余Latest；q1只有Latest。每次更新实际改变该文件所有单元值，输入跨轮/q不同，相应三路完全相同。

对齐的是提交后的版本/结果语义、显式持久化确认与关闭重开。FS-scan 也维护 source/head 目录；FS-index 额外提取并维护 units，每次只提取一个新文件。IoTDB-FS 使用其当前公开发布和查询接口。文件复制/hash/同步、索引更新、查询、SQLite checkpoint或独立实验数据库FLUSH、关闭均进入相应完整轨迹墙钟。不能将三种不同内部同步实现声称为相同断电故障模型。

## 验证与统计

每条查询在计时后逐项验证源身份、精确版本、unit、values/masks摘要和owned状态；关闭后重开检查24份历史文件及Latest/v1结果。总时间直接测量，不相加阶段中位数。所有54条必须完整、全部oracle通过、显式checkpoint/FLUSH完成且资源恢复后，才生成最终表。

完整生命周期报告三轮算术均值、中位数、范围及原值；查询按每轮分布报告，进一步区分更新后首查、v1后首个Latest和其余请求。后两类不能混称首次刷新。FS discovery包含刷新而非刷新独占时间；IoTDB发布确认中的目录绑定也可能预热元数据，须与发布成本一起解释。

本机 Claude Opus 5.5 静态复审完成，未发现负载/计数/总时钟错误；提出的共享DB顺序效应、查询分层、资源差分、失败拒绝和表述问题已纳入分析/说明。其未执行本轮实验。协议测试2项、既有资源创建/迁移/恢复测试15项通过。

本轮补上了原意见要求的持续维护FS-index路径：它并未因计入发布/维护而失去本地优势。HDF5 q1两条FS路径基本相当，差异不足以解释为明确收益；q10/q100的扫描节省随查询次数扩大。IoTDB-FS在这组小文件负载中由发布成本主导，不能用管理能力论证其执行成本更低，也不能用三点外推精确回本阈值。阶段波动中FS-index的更新时间有时低于FS-scan，不构成“增加索引可降低发布成本”的因果证据。

FS-index最终SQLite为124KiB，FS-scan版本目录为100KiB，前者包含96条unit以及共同的24条source/version信息；两者checkpoint后WAL=0。重开连接会产生32KiB SHM。此处不将124KiB全归为语义unit成本，也不与只统计原生文件的IoTDB空间字段作完整空间比较。

### 后台活动与统计边界

FS-index的18条轨迹期间，DataNode CPU时间/轨迹墙钟为0–0.028核，中位数0.013核；FS-scan为0.007–0.506核，中位数0.013核。GRIB q1某轮FS-scan达到0.506核，说明顺序效应确实存在，不能宣称完全排除了数据库后台干扰。两条FS路径期间DataNode物理读字节均为0，仍有少量写入；逐轮CPU/读写计数已保存。IoTDB-FS区间DataNode平均约0.306–0.389核，CPU指标不是用户态查询线程的独占归因。当前结果是共享实例下的描述性比较，不是严格隔离后台状态的因果实验。

### 发布成本的进一步归因

用户追问IoTDB-FS高成本后，读取18条数据库轨迹已有的`mount/publication.jsonl`，没有重跑实验。每条轨迹均有48次成功后端publication：8次`empty_create`、16次`content_commit(source_bytes=0)`、24次非空内容提交。非空提交的version集合与24次业务发布收据完全一致。当前POSIX `open(...,'wb')`路径先创建空文件或提交截断状态，随后`fsync`提交真实内容；FS-index的显式publish直接从暂存文件发布。因此**对齐的是24次业务发布请求、查询时的科学版本与最终结果，不是后端物理版本事件数或并发写入期间的中间可见状态**。不得将本轮说成三路都只产生每路径3个后端版本；M2还需单独对齐并发可见性。

因而这组高成本首先暴露了当前POSIX发布接口与版本管理实现的固定开销，不能作为数据库语义索引本身必然昂贵的理论证据。空版本是否可合并，需要先验证POSIX可见性及故障语义；不能直接从正式总时间扣掉这些阶段，伪造优化后结果。另需注意q100的GRIB纯查询总和为IoTDB-FS6.749s、FS-scan35.823s，仍有发现复用收益；HDF5为8.791s对4.815s，查询侧也存在开销。本轮更接近旧单文件实验中的“发布＋查询生命周期”部分，但仍是8文件跨文件/跨版本负载。相比旧GRIB大文件4,598条message的扫描，本轮每文件4单元、8文件，发现节省绝对量小，难以摊薄高频发布成本；旧单文件纯暖查询不可与本轮总时间直接比较。

## 解释边界

三轮使用不同输入和namespace，但共享DataNode及一次新建的实验数据库，并非完全独立统计样本。固定轮换并未完全平衡前驱效应，须检查FS区间内数据库后台CPU/IO。三轮只能作描述性比较，不提供显著性保证。各q历史比例/首查构成不同，不从这三点直接拟合精确回本阈值。IoTDB同步profile日志、服务启动/卸载等待等实际成本保留在时钟内；原始profile.properties和有效profile归档，不声称观测开销相同。

本轮 N8、固定小输出、单客户端串行发布/查询、缓存不清空。M2并发发布与M3超缓存/网络边界尚未执行；M0进程故障验证不能替代这两项性能证据。IoTDB native_file_bytes不含TsFile/WAL，不能用它做完整三路空间对比。

旧4.3/4.4查询矩阵无需因v2出现而全量重跑。可在相同冻结case上增列v2，再对正文使用的代表点补同期三路；不得把新FS时间除以旧IoTDB时间冒充同期R。S1/S2非命中单元超出v2当前4096值发布profile，继续保留旧静态实现结果，不能声称v2已覆盖。
