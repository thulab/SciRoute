# GEOS single-file rerun after HDF5 adapter review (2026-10-07)

The public GEOS-5.7.2 `/T` direct-query pilot was rerun on `root@192.168.99.49` against the same IoTDB database, exact source version, `D-request-6.json`, and `geos_pilot_direct` path D. Each independent process ran six passes of point, 16×16 ROI, 160×160 multichunk, and five-level extraction. Passes 1–5 are warm observations; pass 0 is retained only for cold-path inspection. Path D includes in-process catalog/source access, HDF5 planning, cursor execution and owned result copy; it excludes socket, FUSE and IPC encoding.

The [previous run](../hdf5-adapter-review-results/D-previous.jsonl) predates the error-attribution and object/link lookup cleanup. Four independent runs of the final binary are [r1](../hdf5-adapter-review-results/D-review-r1.jsonl), [r2](../hdf5-adapter-review-results/D-review-r2.jsonl), [r3](../hdf5-adapter-review-results/D-review-r3.jsonl), and [r4](../hdf5-adapter-review-results/D-review-r4.jsonl). All 96 current query results match the previous run in source, dataset, rows, missing-value count, value-byte count and FNV-1a hash.

| Warm metric | Previous run | Current runs r1–r4 |
| --- | ---: | ---: |
| End-to-end median over 20 queries per run | 4.840 ms | 4.526, 4.776, 4.741, 4.675 ms |
| `prepare` median | 4.665 ms | 4.262, 4.564, 4.452, 4.453 ms |
| `typed_source_open` median | 4.573 ms | 4.157, 4.462, 4.322, 4.355 ms |
| Median of each query's `prepare − typed_source_open` | 91.9 µs | 109.1, 115.5, 111.4, 97.5 µs |
| Layout SQL / manifest SQL per warm query | 0 / 1 | 0 / 1 in every run |

The current run medians are modestly lower in total, but the decrease tracks the changing source-open time. The residual planning time, which includes the revised dataset lookup, did **not** decrease. The first point query in each process took 28.1–30.4 ms versus 29.4 ms previously; its layout-read count remained three. With only one earlier campaign and no interleaved old binary at this exact revision, these timings cannot establish a causal speedup. The reproducible conclusion is that the cleanup preserves results and I/O counts, while a performance benefit on this GEOS single-file workload is not discernible above source-access variation. Larger object/link directories or high-rate in-process queries may be a better workload for evaluating the new lookup maps.

The original B path (the same Adapter against a local payload) was run in three more independent campaigns: [b1](../hdf5-adapter-review-results/B-review-r1.jsonl), [b2](../hdf5-adapter-review-results/B-review-r2.jsonl), and [b3](../hdf5-adapter-review-results/B-review-r3.jsonl). All 72 B results match D in row count, mask count and value hash. Warm end-to-end medians were 0.179, 0.191 and 0.206 ms; `prepare` medians were 65.8, 71.6 and 69.6 µs, of which local source opening was only about 3.3–3.6 µs. There is no immediately preceding B binary at the exact pre-cleanup revision, so these numbers bound the size of the planning work but cannot establish a before/after speedup. Even eliminating this entire B planning interval would save at most about 1.5% of a 4.7 ms D query, before considering that much of the interval is unrelated to the object/link lookup.

The existing published source was also exercised through the original socket registration + FUSE IPC reader with `attr_timeout=1,entry_timeout=1`, without republishing the file. Three independent 24-query campaigns are [e1](../hdf5-adapter-review-results/registration/e1.json), [e2](../hdf5-adapter-review-results/registration/e2.json), and [e3](../hdf5-adapter-review-results/registration/e3.json); every IPC value SHA-256 matches native h5py. The warm point-query end-to-end medians were 45.585, 39.104 and 34.472 ms, split into registration 29.723/24.650/22.406 ms and IPC read 16.779/14.454/12.415 ms. The spread across consecutive campaigns is substantial. In the [third campaign's server profile](../hdf5-adapter-review-results/registration/e3-profile.jsonl), every warm query made four metadata SQL calls, zero layout calls and zero payload calls; median server-side registration was 21.909 ms. The [original pilot's attr-timeout-1 record](../hdf5-adapter-review-results/registration/old-attr1.json) had a 72.366 ms warm point median, but it predates several larger catalog, authorization and layout-cache optimizations. That historical difference must not be credited to this small adapter cleanup.

For the full A–E comparison, native A and mounted-file C were rerun against the same raw and published files using the [read-only replay script](../../tests/benchmarks/hdf5_query/geos_pilot_readonly.py), in three independent campaigns: [a1/c1](../hdf5-adapter-review-results/read/a1c1.json), [a2/c2](../hdf5-adapter-review-results/read/a2c2.json), and [a3/c3](../hdf5-adapter-review-results/read/a3c3.json). They matched each other by SHA-256 in all 72 observations. The table reports the median of each path's independent warm-campaign medians, in milliseconds; each campaign has five retained-cache passes per case. C and E used `attr_timeout=1,entry_timeout=1` on the new temporary mounts. A and C do not use the typed Adapter and are environment controls, not optimization targets.

| Query | A native | B local Adapter | C mounted-file HDF5 | D IoTDB typed | E registration + IPC |
| --- | ---: | ---: | ---: | ---: | ---: |
| Point | 0.817 | 0.127 | 33.581 | 4.423 | 39.104 |
| 16×16 ROI | 1.257 | 0.157 | 34.597 | 4.665 | 40.020 |
| 160×160 multichunk | 1.236 | 0.282 | 33.834 | 4.906 | 42.366 |
| Five levels × 16×16 | 3.774 | 0.194 | 102.479 | 4.620 | 38.943 |

The five paths preserve the original qualitative order: preindexed local Adapter B is fastest, typed IoTDB D avoids much of mounted HDF5's C-path overhead, and E still pays substantial registration and FUSE result-open costs. The table reflects the cumulative implementation since the original pilot. It does not isolate a speedup from the latest error-handling and directory-lookup cleanup.
