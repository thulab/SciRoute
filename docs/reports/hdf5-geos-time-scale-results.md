# GEOS 跨文件时间筛选：16 个真实时次的配对实验

> 文档整理：标为“服务器归档”的引用按本次清单不再作为 Git 文档保留，查验路径见 [文档归档说明](../README.md#服务器归档)。

2026-10-07，在扩容 DataNode 之前，使用 NASA 公开的 GEOS-5.7.2 `inst3_3d_asm_Np` 原件验证「从多个 HDF5 文件中按 UTC 时间选出一个版本」的查询。**时间目录确实把 N=16 时的 catalog 读取从 16 份减为 1 份，但目前没有取得相对普通文件系统的端到端速度优势。** IoTDB-FS 仍为全部 16 个候选做 manifest/授权元数据工作；时间筛选节省的主要是 HDF5 dataset catalog 的读取与属性谓词查询。

## 数据与方法

[NASA GMAO 公开目录](https://gmao.gsfc.nasa.gov/gmaoftp/ops/GEOS572_Sample_Data/inst3_3d_asm_Np/)中的 2011-07-01 至 07-02 共 16 个连续三小时时次均为不同的完整原件，合计 **7,142,773,610 B**。逐文件核对 SHA-256、HDF5 结构、`/time` 的 UTC 坐标和 dimension-scale 证据；冻结清单见[原件 manifest](../results/hdf5-geos-time-scale-20261007/source-manifest.json)。此前同名但只有数 MB 的截断文件未计入。16 个原件摄取到服务器 `/data_01/zzy/iotdb-fs-exp` 的隔离数据库 `geostime20261007`，成为带 `utc-point/1` 覆盖标记的精确版本；[摄取记录](../results/hdf5-geos-time-scale-20261007/pilot.json)确认全部完成。摄取与普通 FS 时间目录的构建均不计入在线查询时间。

固定目标为 **2011-07-02 09:00:00 UTC**，半开区间 `[1309597200, 1309597201)`；N=1、4、8、16 的每组均包含这同一个真实目标，以及距离它最近的其他真实时次。对照查询使用相同的 `/T` 路径和 `standard_name=air_temperature` 属性条件。每组另测一个无命中的时间点，以及不带时间条件、只按属性筛选的 IoTDB-FS 请求。单客户端顺序查询；独立启动三次挂载，每次对每组的命中和未命中各重复五次。下表「暖态」是每次挂载的第 2–5 次，共 12 次样本的中位数；首次结果仍保存在[完整记录](../results/hdf5-geos-time-scale-20261007/scale-campaign-3x5/report.json)中。所有 15 次/组的身份集合均与普通 FS 对照一致：命中 K=1、未命中 K=0。无谓词的跨文件目录发现及其成本单独报告，不把它记作时间剪枝。

普通 FS 有两条对照：**预建时间目录**在构建时对所有原件做 hash 与语义验证，查询时只对选中的文件检查大小及 mtime；**原生逐文件扫描**每次重开候选 HDF5 文件、读取和验证时间坐标后作选择。前者给双方相同的已验证时间索引语义，后者是无预建目录的现实开销。两者均是本机 Python 控制程序，IoTDB-FS 还承担注册 socket、查询服务及数据库调用；这些系统边界需连同结果一起理解。普通 FS 目录大小 **8,363 B**，构建含全部原件 hash/语义验证耗时 **17.145 s**；16 个 IoTDB-FS 版本的 publish 耗时之和 **136.75 s**，另占用存储，均是离线成本。

2026-10-10 已按相同原件、顺序和发布计时边界完成完整发布复验（服务器归档：`docs/hdf5-geos-publish-repeat-20261010.md`）：当前单轮耗时 **147.762927 s**，历史单轮为 **136.750588 s**，未观察到发布提速。16 个新版本的 layout SHA 与旧版本一致，64 次原生／IoTDB-FS 值校验通过；这不是冻结旧二进制的配对消融。

同日按原 3×5、零 TTL 配置完成查询阶段整体复验（服务器归档：`docs/hdf5-geos-query-overall-20261010.md`）：N=16 时间命中发现 **165.520→150.742 ms**，未命中 **132.565→117.515 ms**；144 个目录／取值请求累计计时 **15.896→13.942 s**。普通 FS 原生扫描仍更快，目录授权仍逐源读取。这些是查询阶段的历史／当前结果，不是从 raw 到两侧最终消费的统一发布＋查询总时间。

### FS 预建目录计时口径复核

[`search()`](../../tests/benchmarks/hdf5_query/geos_time_directory.py) 接受已解析到内存的 8,363 B JSON 目录，计时器在读取、解析和构建目录**之后**启动。它线性检查最多 16 个 `utc_second`；命中时只对**命中的文件**做一次 `stat` 并比较大小、mtime，未命中时连 `stat` 也没有。不包含逐候选源授权、文件内容 hash、`H5Fopen`、`H5Dread`、查询 socket、进程边界或 IPC。构建目录时还已固定验证 `/T` 与 `standard_name=air_temperature`，运行时不再执行可变 dataset 属性谓词。因此 0.002–0.007 ms 是专用内存时间谓词的未命中成本，**不是完整的 FS 文件查询时间**；命中时正式实验的暖态中位数为 0.061–0.066 ms。数字计算无误，但把这列称作与 IoTDB-FS 通用目录接口对等的端到端查询会误导。

在同一服务器对 N=16 命中路径另做 2,000 次暖态只读微测，分离成本：仅内存选择中位数 **1.26 μs**；选择加目标 `stat` **9.17 μs**；每次重读并解析 JSON、选择及 `stat` **67.52 μs**；选择、`stat`、打开原件并读取 8 B header **20.57 μs**。微测与正式实验运行环境不同，不用其替换上表；它确认了这种索引本身极小且被页缓存覆盖。严格的“查找并取值”至少还需计入原生 `H5Dread`（本实验单点中位数 1.298 ms），而 IoTDB-FS 对应的是目录请求、再执行 typed 查询的两段服务链路。FS 索引构建的 17.145 s 与内容 hash 也只作为离线成本报告。

这里的索引特别简单：GEOS 每个文件只有一个已验证 UTC 时点，等价于时间点到精确版本的微型目录。换成二分或哈希索引只会使 FS 查找更便宜；扩大 N 并不能自动产生 IoTDB-FS 相对同等索引 FS 的优势。后续应以相同的候选证明、授权边界和结果值，分开比较索引查找、源验证、物理数据读取及完整接口时间。

### IoTDB-FS 控制请求与目录查询的 wall time

[`geos_time_scale.py`](../../tests/benchmarks/hdf5_query/geos_time_scale.py)每个样本都新建 Unix socket 连接，提交完整的 `dataset_catalog` JSON，并等待结果。服务端的该分支直接调用 [`discover_datasets`](../../src/IoTDBStructuredBlobBackend.cpp) 并返回 JSON；**没有注册持久查询路由、没有 prepared ID，也没有将先前请求的选择或授权结果用于下一次请求**。profile 中的 `registration_total`、`registration_attempts` 是控制入口的通用名称，不应解释为另有一项昂贵的可复用路由注册。各组第 2–5 次请求仍执行相同数量的元数据查询。

以下为 3 次挂载 × 4 次暖态请求的中位数，单位 ms。`发现`包含授权；`授权`包含在 `IoTDB 元数据调用耗时`内，这些列**不可相加**。服务端总时长不含收发 socket frame 与 profile 写盘。

| N、结果 | 客户端总时长 | 服务端发现 | 其中源与父目录授权 | 扣除授权后的发现¹ | IoTDB 元数据调用耗时 | 客户端与服务端差 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1、命中 | 57.137 | 56.626 | 11.680 | 45.367 | 53.469 | 0.519 |
| 1、未命中 | 23.692 | 23.134 | 11.846 | 11.340 | 21.783 | 0.487 |
| 16、命中 | 165.520 | 164.783 | 72.401 | 91.833 | 155.793 | 0.675 |
| 16、未命中 | 132.565 | 131.633 | 73.504 | 58.302 | 124.914 | 0.666 |

¹ 对每条记录计算 `dataset_catalog_discovery − authorization_source_metadata − authorization_parent_metadata`，再取中位数；这是分析性拆分，**不是一个已实现的免授权查询 API**。N=16 命中有 40 次 IoTDB 元数据调用，其中 18 次来自对 16 个源及两个共用父目录的授权；时间未命中仍有 35 次调用。服务端先查询完整 published manifest 快照，授权全部已选源，再逐源重读 manifest 核验版本；只对时间命中的源加载 catalog、校验二级索引计数并运行属性谓词 SQL。N=16 命中相对同组未命中，配对服务端耗时的中位增量为 **33.542 ms**，可视为加载与验证一个命中 catalog、执行属性筛选及返回结果的组合增量，**不是单条谓词 SQL 的独立计时**。

该控制请求的 JSON 解析在 N=16 命中时中位数仅 **0.060 ms**，请求帧为 **1,261 B**；客户端与服务端差约 **0.675 ms**。所以消除 socket/JSON/路由注册不可能解释 165 ms，重复的逐源授权、manifest 验证和 catalog SQL 才是主要工作。若未来引入可复用的候选集或权限缓存，应另测其构建、失效和每次查询成本，不能从此表直接宣称缓存后的真实延迟。

不带时间条件的同属性查询在 N=1/4/8/16 时，三次挂载的客户端中位数依次为 **57.277/188.508/342.915/680.996 ms**，catalog 读取为 **14,661/58,644/117,288/234,576 B**，元数据 SQL 为 **7/25/49/97**。因此 N=16 的时间命中将 catalog 读取减少 **93.75%**、SQL 次数从 97 降到 22，并将本系统的目录延迟从约 681 ms 降至约 166 ms，约 **4.1 倍**。这是相对 IoTDB-FS 无时间谓词路径的收益，并非相对 FS 的胜出。

N=16 的时间命中仍有 **40 次元数据查询**，其中授权相关的 source metadata 检查为 **16 次**，并有选中 manifest 的版本验证；时间未命中也仍有 **35 次元数据查询**。这解释了目录延迟仍近似随 N 增长：`utc-point/1` 在 catalog 读取前筛除 15 个文件，却不是能跳过全部候选 manifest/授权的全局数据库时间索引。发现请求的 payload 调用为 0，不能把省掉的原文件大小当作实际 I/O 收益。

为检查发现后的取值链路，每次挂载和 N 组又对选中精确版本执行一次 `/T` 单点 typed 查询。**12/12** 次 IPC 中的 Float32 值与原生 `H5Dread` 的 SHA-256 相同，均返回一行；typed 客户端中位数 **107.667 ms**，原生单点 `H5Dread` **1.298 ms**。每次 typed 查询读取一个压缩 payload 范围、**12,415 B**，IPC 结果 **5,752 B**。这是独立的取值计时，不应与上表中不同样本的目录中位数简单相加为严格配对的完整查询时间。首个 typed 请求为冷态 **377.710 ms**，原始记录保留该值。

作为与目录发现不同的口径，12 次单点 typed 请求的**服务端**中位数为 **40.641 ms**；其中 cursor 执行中位数 **4.081 ms**，prepare **12.395 ms**，路由 materialize/publish **16.961 ms**。各 stage 存在嵌套，不可相加。客户端的 107.667 ms 还包含返回只读路径后的 FUSE `memory_map`、Arrow IPC 读取和数组转换；不能把它称为纯物理 chunk 查询耗时。

## 判断与边界

实验确认了在真实 GEOS 时次上，经过属性和 dimension-scale 验证、绑定精确版本的 UTC 标记可正确完成跨文件时间剪枝，并显著减少 **IoTDB-FS 自身**的 catalog 工作；生产 `/5` 物理查询也只取命中的一个 chunk 范围。与此同时，N=16 时 IoTDB-FS 的 **165.520 ms** 目录延迟高于普通 FS 的预建目录 **0.066 ms**，也高于逐文件原生扫描 **46.593 ms**。这组数据支持「语义剪枝有效、当前系统固定及逐候选元数据成本仍占主导」的判断，尚不支持「GEOS 时间目录在 IoTDB-FS 上快于 FS」。公开样本只有 16 个真实时次，不能由此推断 N≥64 的交叉点；亦不能把已有的文件内 chunk 剪枝优势直接归因于跨文件时间索引。

复现实验入口是 [`geos_public_acquire.py`](../../tests/benchmarks/hdf5_query/geos_public_acquire.py)、[`geos_scale_verify.py`](../../tests/benchmarks/hdf5_query/geos_scale_verify.py) 和 [`geos_time_scale.py`](../../tests/benchmarks/hdf5_query/geos_time_scale.py)。[原始运行目录](../results/hdf5-geos-time-scale-20261007/scale-campaign-3x5)保存 12 个挂载的服务端 JSONL、挂载日志、FS 索引和逐请求计时；计时与文件版本身份可从中重算。没有扩容 DataNode，也没有修改 GRIB 基线数据库。

后续[累计修复复验](hdf5-geos-cumulative-20261010.md)保留同一16原版本和请求次序：N=16暖态时间命中153.493→41.533 ms、未命中123.540→12.497 ms、首次仅属性621.515→127.032 ms。这是精确`0a62f6e`与当前版同轮配对；本报告未冻结旧daemon的历史值另列，不冒充exact commit。
