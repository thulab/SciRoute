# 第一阶段大 N 优化：固定组 A/B 验收

结论：第一阶段公共模块修改及 N8／N128／N512 六个固定组测试已完成，正确性、独立结果审计与资源恢复均通过；大 N 完整查询性能验收未通过。N512 的 GRIB 发现耗时有所下降，但完整查询及相对成本改善不稳定；HDF5 完整查询中位增加 16.80%，四轮中三轮变慢。候选代码保留在工作区及归档供复核，未替换已接受二进制或原运行挂载，不将本轮登记为已接受性能基线。

## 1. 实现范围

本轮针对已有显式路径协议中的重复工作，修改 13 个产品文件：

- `SourceSelector.paths` 改为不可变共享的 `PathScopeSet`。构造时完成路径规范化、校验、排序和身份字符串编译，后续复制共享编译结果；精确路径匹配使用二分查找，子树匹配保持原语义。原始遍历顺序、身份编码及版本／路径／格式错误的校验次序保持一致。
- `CatalogSelection` 的候选 manifest 数组不可变共享。副本固定同一候选快照，替换其中一个 selection 不改变其他副本；HDF5 补充信息通过构造新数组替换，避免修改缓存中的候选骨架。
- `QueryModule::prepare` 同步借用调用方提供的 selection；owner 前端保留 `read_context` 并借用完整来源数组，strict 通路持有自己的来源引用。执行、发布及后续打开的权限检查与预算仍按原规则执行。

本轮未引入 scope_id，未改费用回放的表示、缓存容量或线程数。显式路径输入和部分候选遍历仍随 P／C 增长；不能据此宣称完整热查询已达到 O(log N)。V／K 超出热容量的问题属于后续阶段。

## 5. 公共模块覆盖与 HDF5 重复工作核对

用户指出 HDF5 暖发现原已直接引用 domain，这一点经源码和全部正式发现 profile 核对成立。三档、A/B 共 240 条 HDF5 正式发现记录均为 domain_hits=1、index_lookups=1、proof_hits=2、admissions=2、IoTDB query_calls=0；N512 选择源为 512、候选 dataset 为 2,048。不存在本轮才把暖发现改成直接引用 domain 的收益。

| 修改／环节 | GRIB 与公共 typed 路径 | HDF5 暖发现 |
| --- | --- | --- |
| `CatalogSelection` 不可变共享 | 避免候选 domain 返回及后续选集副本深复制 | 命中 `HotCatalogDomain` 原已借用 selection／sources／index，这项没有直接命中路径收益 |
| `QueryModule::prepare` 借用、owner 来源引用复用 | 优化公共规划、物化和发布中的副本 | `dataset_catalog` domain 命中不经过 `prepare`；取值 typed 通路另受影响 |
| `PathScopeSet` | 公共 selector 类型；复制可共享规范化与身份 | 每个新 JSON 请求仍构造完整 scope；同一请求内复制共享，不跨请求复用编译结果 |
| 精确路径二分匹配 | 普通 catalog 匹配可受益 | domain 命中直接查属性 index，不执行这一匹配循环 |
| selection／manifest／catalog／proof 费用 | 使用既有预算账本和批次回放 | 本轮未修改；新请求首次回放仍逐身份查账，相关成本随费用条目数增长 |

重复工作需分开判断：

1. `PathScopeSet::Compiled` 当前先建立 `std::set` 校验唯一性，再排序索引并编码 key。这里有可合并的排序／临时结构工作；其重建仍发生在每个外部请求。入口与 backend 仍各调用校验，但路径部分读取已编译状态，不再次遍历编译。不能把“同一请求副本复用”写成“热 domain 消除了 selector 构建”。
2. `owner_domain_key` 仍把完整路径身份串追加到 key，并由缓存查找处理该字符串。规范化／排序移入编译阶段，并未让每次 key 构造变成常数成本。
3. `selection_fees`、`manifest_fees`、`catalog_fees` 及权限 proof 仍按原控制阶段回放。预算按身份的已观察最大值去重；同一 `PreparedQueryMetadataTrace` 在同一预算内还有批次记忆。已有去重不等于消除了不同费用批次首次回放的逐项比较、查账与新身份分配。不能把这些调用直接解释为重复收费。
4. 发现授权与返回响应前的 admission 各执行一次，profile 的两次 proof_hits 与之对应。后者用于响应发布时检查命名空间状态，不能因为表面重复就删掉；同一 proof 批次的二次回放已有预算内记忆。开启嵌套 trace collector 时还必须向 collector 传播证据，不能无条件跳过。

源码入口：[selector 编译](/Users/alan671/Documents/FS-paper1/IoTDB-FS-C/src/query/core/QueryPlanning.cpp:439)、[HDF5 domain 命中及费用顺序](/Users/alan671/Documents/FS-paper1/IoTDB-FS-C/src/IoTDBStructuredBlobBackend.cpp:2935)、[预算去重和批次记忆](/Users/alan671/Documents/FS-paper1/IoTDB-FS-C/include/iotdbfs/query/core/QueryMetadataBudget.h:74)、[响应发布前 admission](/Users/alan671/Documents/FS-paper1/IoTDB-FS-C/src/query/frontend/QueryRegistrationSocket.cpp:1419)。

因此，这轮应定位为公共所有权／selector 基础结构改动，不能等同于 HDF5 暖发现的主要瓶颈优化。后续应先针对 selector 的每请求编译／key 构造与费用首次回放分别测量，再考虑合并编译过程和构造可复用的费用执行计划；需保留精确来源／版本语义、预算超限行为、权限与命名空间变化的检查。当前证据尚不能把 HDF5 的 +16.80% 因果归结为某一个内部步骤，本轮没有修改冻结候选或追加实验。

## 6. 资源、恢复与证据边界

独立资源审计通过，三档分别核验 1,095／2,115／5,509 个周期与逐行组合快照，以及 3,285／6,343／16,527 次 owned 进程观测。N128 有一次短暂进程观测缺失，保留缺失状态，未填为零；其余已记录的 CPU／cgroup 策略无越界异常。所有正式查询包络中，parent／query／database 的限流、OOM 与 OOM kill 增量均为 0。

其他 30 个 guest vCPU 的各块忙度范围分别为 N8 7.98–28.21%、N128 0.44–2.71%、N512 0.67–17.79%；N512 最后一轮 HDF5 的 B 块为 17.79%，对应 A 块约 1.05%。该轮仍保留，不能据此剔除慢值，也不足以将全部变化归因于环境。整个 N512 采集周期的 cpu2／cpu3 steal 分别增加 39／41 ticks；这不是仅查询期间的值。虚拟机不暴露有效频率信息，guest 内隔离不代表物理 CPU、频率、共享缓存或内存带宽独占。

最终额外只读检查确认：原 DataNode PID 4177388，可执行原设置查询，ASYNC／partial-insert=true；239 个线程恢复原 0–31 亲和性及原 cgroup；9 个临时资源组路径不存在，48 个实验挂载均已卸载，旧实验 daemon 已退出。原配置 SHA 为 `f69f408de5c09edabae3a8293cf662327f794b908cbf98d5a02b3878fea154f4`，与采集前字节一致，保留此前已确认的 1% 磁盘阈值；许可证与节点身份摘要一致。

额外核验第一次使用系统 Python，因缺少 pyarrow 在只读依赖加载阶段退出；保留该脚本与空核验目录，改用实际实验 venv 完成核验。没有重启服务、修改科学记录或重跑科学查询。

本轮不作冷盘或并发负载结论。资源包络包括计时外的 oracle／profile／采样，不能当成 d／q 的独占 CPU 时间。局部减少复制不足以单独解释 HDF5 取值耗时的变化。

## 8. IoTDB-FS 自身成本的区间斜率（补充分析）

针对用户后续问题，以 `s=(t(N_high)-t(N_low))/(N_high-N_low)` 计算区间有限差分。每个 campaign 使用该 N／配置的正式记录中位耗时，先得到 A、B 的斜率，再计算同轮 B/A，最后取四轮中位数。下表为斜率变化百分比，不是相对 FS-index 的 R，也不是 N512/N8 的耗时增长倍数。

| 格式 | N 区间 | 发现 d 斜率变化 | 完整 T 斜率变化 |
| --- | --- | ---: | ---: |
| GRIB | 8→128 | -20.37% | -20.31% |
| GRIB | 128→512 | -4.64% | +18.05% |
| GRIB | 8→512 | -7.43% | -2.01% |
| HDF5 | 8→128 | +5.73% | -38.02% |
| HDF5 | 128→512 | +19.86% | +26.06% |
| HDF5 | 8→512 | +21.30% | +23.48% |

GRIB 的 8→512 发现斜率四轮均下降，中位 −7.43%；完整查询斜率仅约 −2.01%，且 128→512 区间增加 18.05%，不能称为完整查询的稳定降斜率。HDF5 的 8→512 发现及完整查询斜率分别增加 21.30%、23.48%；128→512 区间也都上升。整体不支持本轮已降低大 N 完整查询斜率。

这只是三个独立 N 档位的描述性补充分析；P=C=N 联动，且不同 N 顺序采集，不能解释为纯 N 因果效应、渐近复杂度改变或统计显著性证明。逐轮斜率及输入 SHA 保存在本地 `slope-analysis.json`，未追加科学查询。
