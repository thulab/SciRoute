# 有界跨请求 payload 块缓存与大 S 短探针

本轮完成了请求内／在途块共享向跨请求 LRU 驻留的扩展，保留版本、权限、逻辑预算、取消、错误和引用释放边界。最终版本通过全部 2,115 项单元测试及 22 项启动配置检查。复用文档 4.3 的四个 H3 S1／S2 封印实验组完成 120 次完整查询，独立结果审计及实际服务恢复核验均通过。

**这轮性能探针没有证明新增块缓存带来加速。** GRIB 后续请求在 OFF 时已经不再读取底层 Store；HDF5 当前使用原生文件读取，不经过数据库 payload。耗时差异全部保留，但不能把它们归因为块复用收益，也不能据此保证 S 增长时成本平滑。

随后针对 GRIB S1／HDF5 S2 的慢化补充了线程及硬件计数诊断，见[独立诊断报告](payload-cache-regression-diagnosis-20261027.md)。以下原始数据保留，不以诊断复放替换。

## 实现和边界

- 配置 `storage.version_directory.payload_cache_bytes` 默认 8 MiB，范围 0～8 MiB；设 0 只关闭跨请求驻留，保留既有请求内和在途共享。`payload_read_coalescing=false` 关闭整个块共享机制；严格模式拒绝这些配置。
- 每个 Owner 的在途块、LRU 驻留块、驱逐后仍被消费者持有的块共用原来的 **64 条目／8 MiB 块数据上限**，不另加一份缓存额度。仅完整校验成功且缓冲容量等于精确块长的块可驻留；身份包含 Owner 运行时、namespace、incarnation、类型、协议、content ID 和大小。容量不足先撤销可选 LRU 引用，活跃引用无法释放时真实读取旁路。
- 不缓存查询答案、可变 head 或失败结果，不拆分原生 Store batch，不增加客户端 worker 或查询内线程。每个消费者仍获得私有输出，版本／权限准入与逻辑 I/O、payload demand 费用不因命中减少；force／深度完整性检查绕过缓存。
- Entry 保留生产者原有的完整临时内存预约，最后一个引用释放才退款。运行时固定 64 槽 weak 注册表在初始 loader、temporary、metadata 预约压力下回收可选驻留；回收和析构在预算／块注册表锁外进行。活跃引用继续计费，真实不足仍走原错误路径，不重试已失败的预约。
- `clear_read_cache()` 和恢复清除可选驻留，generation 阻止旧生产者在清除后重新驻留。Owner 析构在销毁运行时、锁和计数器前先撤销驻留，避免预算 pin 释放重入已经销毁的运行时。

详细协议及计数口径见[块共享契约](../contracts/payload-read-coalescing.md)。8 MiB 是块数据上限，**不是临时预约或进程 RSS 上限**；原物理 batch 的完整预约可能是块数据的四倍。

## 条件与计时

采用[实验文档](https://apache-iotdb-project.feishu.cn/wiki/Kx87wsVXpiB5aUkYG50cCKoEnmg) revision 1119 的 4.3 H3 行。H3 只扩大非命中 unit，不扩大命中输出；不是 4.2 大型真实文件组，也不是多版本组。

| 注册行 | 格式 | 每文件大小中位数，B | 仅非命中 unit 的网格 |
| --- | --- | ---: | --- |
| G-H3-S1 | GRIB | 1,180,364 | 384×384 |
| G-H3-S2 | GRIB | 4,719,308 | 768×768 |
| H-H3-S1 | Native HDF5 | 1,607,188.5 | 384×384 |
| H-H3-S2 | Native HDF5 | 6,337,470 | 768×768 |

四组均固定 N=8、V=1、C=P=Cv=8、D=4、Latest、原六个等值谓词，命中文件／文件版本／unit 为 2／2／2，命中 unit 为 64×64，完整 values＋mask 输出为 40,960 B。复用原 corpus、case、文件字节、SQLite 索引和发布身份，只新增 run，没有重新发布、建索引或更换查询。

同一个最终二进制切换 OFF=0／ON=8,388,608，其他查询参数相同。一个客户端顺序发送请求；公共 worker／Owner reader／sender 容量固定为 4／4／1。两轮分别 OFF→ON 和 ON→OFF，第二轮反转组顺序；每个配置独立新挂载，每组每轮各执行首次 1 次、预热 1 次、测量 3 次。每组每轮另有一个新 FS-index context 的同样五次只读查询，放在两个配置之间，共享为该轮对照，不冒充两份独立配对基线。

共 16 个挂载、80 次 IoTDB-FS 查询、40 次 FS-index 查询、24 个注册 run；72 次测量、24 次首次、24 次预热，无剔除和补跑。固定 CPU 2／3、共享两核配额、查询叶组 2 GiB；DataNode 堆／direct 另计为 15,232／2,176 MiB。两轮只作描述性探针，不声明显著性或稳定尾延迟。

`T=d+q`，d 为发现，q 包含全部命中单元读取至客户端拥有完整数组及 mask；oracle、profile 和资源快照在 T 外。首次表示新 daemon／context，**不表示冷磁盘或冷 DataNode**，未清 OS／数据库缓存，也未关闭上层解码缓存来人为制造块读取。HDF5 保持当前 native-hdf5 文件系统后端、K=2 batch、native cache=false、read parallelism=1，数据库 payload 读取为零。

## 机制证据与解释

Store 数字是查询区间的 SDK 调用／返回 BLOB 字节，包含元数据和 payload，**不是物理磁盘 I/O**。本轮客户端顺序查询，可以汇总发现和值读取阶段；并发运行不能沿用这一加总方法。

| 组 | 首次 OFF／ON：SDK 调用数 | 首次 OFF／ON：BLOB 字节 | 所有后续 OFF／ON：SDK 调用数 | ON 后续 temporary gauge，B |
| --- | ---: | ---: | ---: | ---: |
| G-H3-S1 | 2／2 | 1,787,288／1,787,288 | 均为 0 | 7,149,152 |
| G-H3-S2 | 2／2 | 1,450,700／1,450,700 | 均为 0 | 5,802,800 |
| H-H3-S1 | 0／0 | 0／0 | 均为 0 | 0 |
| H-H3-S2 | 0／0 | 0／0 | 均为 0 | 0 |

首次数字在两轮中完全一致。GRIB 的块／生产者预算在 ON 下确实跨请求保留，但后续请求已被上层已有缓存覆盖，新增块驻留没有可供消除的重复 Store 读取。原生 HDF5 的查询从受管文件读取，不能借此检验数据库 payload 缓存。S2 扩大的是非命中内容，不能把文件总体大小等同于本次实际 payload 需求；本次 S2 首次返回字节甚至低于 S1。

80 次 IoTDB-FS 查询的同步 profile 均没有观察到新增 `payload_cache.*` 计数键，原因是这些读取未暴露相应 TLS 计数。缺键记为“未观测”，不伪造为零次查找，也不能由此证明未调用缓存。可确认的是原始 SDK 增量、ON 预算驻留和内容正确性。所有测量查询的 parent CPU 配额 throttled_usec 增量及 runtime waits 均为零；这只排除这些已观测的等待指标，不能排除其他调度、交付或运行时干扰。

因此，这轮修复提供了有界复用和统一回收的基础能力，**尚未证明解决当前四组的 S 成本问题**。后续若要单独衡量其收益，应使用真实跨请求重叠块、同时不能被上层解码结果直接覆盖的访问序列，并先补齐实际读取线程的观测；不能通过改封印条件、关闭其他缓存或切回旧 HDF5 后端制造收益。当前没有据此增加缓存容量或宣称文件越大收益越高。

## 正确性、恢复与证据

最终 GCC 13 Release 隔离构建包含 `iotdb_fs`、`iotdb_fs_web` 和 `unit_tests`。166 项聚焦测试及全部 2,115 项单元测试通过，无跳过；22 项启动配置检查通过。覆盖独立请求命中、LRU／容量旁路、活跃 pin、压力回收、clear generation、force 校验、身份隔离、冻结、取消、失败批次及析构重入。另有本地 ASan／UBSan 的 91 项块／运行时测试、17 项 Owner 测试和子容量 LRU 检查通过。

构建准备中的失败／替换尝试保留：r1 是新增冻结测试未实际发布导致断言失败，修正 fixture；r2 全套通过后，析构顺序审查及 sanitizer 红测暴露运行时销毁后释放驻留 pin 的问题，r3 修复并通过绿测。本轮只测量 r3，未用早期候选替代或补跑结果。

独立标准库审计核对 4 个 corpus／case、24 个 run、120 次查询、185 个运行闭包文件、完整矩阵、oracle 绑定、216 个阶段统计、资源及恢复收据。客户端在查询时校验完整输出；独立审计没有重新读取未保存的数组。402 次周期资源采样中 274 次覆盖查询区间。只读现场恢复审计确认原配置字节、ASYNC／true、DataNode 进程身份、228 个线程的原 CPU 亲和、原 cgroup／controller、16 个挂载和查询进程退出；审计只另发出一次配置查询，不执行科学查询。原服务已恢复。
