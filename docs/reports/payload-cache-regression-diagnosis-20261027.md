# GRIB S1／HDF5 S2 的 ON／OFF 慢化诊断

本轮针对[大 S 块缓存探针](payload-block-cache-large-s-probe-20261027.md)中的反常慢化继续定位。**可以排除新增块驻留的查找、复制、LRU 淘汰和预算回收造成了所观察到的几倍慢化。** GRIB 测量请求走已有 native-field 命中路径，Native HDF5 根本不经过 payload 块缓存；重复诊断中，异常也出现在 OFF。不能将之前 S1／S2 相反的比值解释为缓存对文件大小的不同收益。

已定位的异常表现是：公共请求执行及登记以外的结果交付链路出现间歇停顿，同样的服务端用户态指令量对应很不相同的墙钟／CPU 记账时间。KVM 环境的宿主停顿或来宾 CPU 记账／虚拟 PMU 口径差异是重要候选；**没有宿主调度记录，尚不能唯一确定停顿来自哪个宿主任务，也没有证据宣布 `kvm-clock` 本身有缺陷。** 本报告不把“未发现新增缓存回退”扩大成任何环境下性能完全不变的保证。

## 原始慢化发生在哪里

使用原始 120 次查询逐项重算。下表每格取该配置完整 T 处于三次测量中位数的那一条查询，再分解其实际调用，避免相加不同样本的阶段中位数。单位 ms。

| 原始组／轮 | 配置 | 完整 T | 各调用 server_total 之和 | T 减去 server_total |
| --- | --- | ---: | ---: | ---: |
| GRIB S1／1 | OFF | 5.933 | 2.215 | 3.718 |
| GRIB S1／1 | ON | 76.899 | 28.440 | 48.458 |
| HDF5 S2／0 | OFF | 10.182 | 5.114 | 5.067 |
| HDF5 S2／0 | ON | 73.029 | 59.740 | 13.288 |

GRIB S1 同时慢在登记内部和外部，HDF5 S2 此例主要慢在登记内部。解析、准备、cursor、Arrow 编码等多个已有阶段一起增加，不能将差值全部归入数据准备、SQL 或 FUSE 中某一个步骤。`server_total` 不含端点 runtime／hot-pool 快照、socket 写回及 profile 序列化／flush；后两者还能与 IPC 和后续请求重叠。因此最后一列是残差，**不是 FUSE／IPC 独占耗时**。

原始请求的业务工作计数、请求长度及 profile 大小基本一致。客户端每次创建新 t0／t1／t2，profile 只按已保存偏移读取新行，未发现累计计时或全量重读旧 profile 的缺陷。三次测量加两轮配对的样本很少；前一报告的单个比例不能作为因果结论。

## 为什么不是 S 触发了新增缓存争用

H3 的 S1／S2 只扩大非命中 unit；N=8、V=1、D=4、Latest、K=2 以及 40,960 B 的完整输出固定。文件总体 S 不是本次 payload 需求，也不等于缓存工作集。格式之间的控制调用结构也不同：GRIB 为一个 format_catalog 加两个 typed；HDF5 为 dataset_catalog 加 K=2 typed_batch。

| 核查项 | GRIB S1 | Native HDF5 S2 |
| --- | --- | --- |
| 实际值读取路径 | 每个测量 value call 均 alias／content hit，loads=0、loaded_bytes=0 | 受管完整文件 → NativeFileStore／pread → HDF5 |
| 后续 Store SDK 读取 | OFF／ON 均 0 | OFF／ON 均 0，格式本来不使用数据库 payload |
| ON 的 runtime temporary | 7,149,152 B，完整生产者 pin 的保守预约 | 0 B |
| 查询预算 | 2,147,483,648 B | 同左 |
| 预算等待／压力回收证据 | 无新增 producer、redecode、内存等待；hot-pool pressure=0 | runtime live／temporary=0；无相关回收路径 |

`PayloadBlockFlights` 构造只设置容量，不预分配 8 MiB，不启动缓存线程。注册表扫描、LRU 和新增 profile 计数只在实际块读取时执行；预算回收只在实际不足时执行。温热 GRIB 的 native-field 命中和 Native HDF5 不执行这些代码。所有观测到的 `payload_cache.*` profile 缺键仍标记为“未观测”，路径判断同时依赖真实 loader／Store 指标和源码，未把缺键当成零次调用。

对应实现位置：GRIB `GribFormatQueryAdapter.cpp` 的 native-field／encoded-loader 分支；HDF5 `Hdf5QueryKernel.cpp` 的 native cursor 和 `Hdf5SourceDriver.cpp::open_local()`；`PayloadBlockFlights.h` 的 `register_cache/read/read_batch`；`DecodedFragmentCache.cpp` 的不足时回收分支。新增缓存没有为这些温热请求增加一条 SQL、解码或块复制路径。

## 三轮诊断：异常不稳定跟随开关

沿用同一最终二进制 `9ce21d6d…b3c987`、原封印 corpus／case、查询和客户端完整数组计时。仍为一客户端顺序请求、两核共享配额、查询叶组 2 GiB，未增加 worker、改查询、清缓存、重新发布或建索引。诊断增加了观察开销，**不替换原正式性能记录**。

- r1：四组、两轮、120 次查询；加线程 `schedstat`、faults 和客户端独立算术校准。首次热点采样没有有效样本，保留原件，不用空结果归因。
- r2：只复用 GRIB S1／HDF5 S2，60 次查询；修正采样器启动时序，等待 enable acknowledgment，再开始查询。各挂载得到有效用户态样本。整体采样含首次读取及 T 外校验，故不将整体热点比例当作某个查询阶段的独占耗时；未验证默认 perf 时钟与客户端时钟的精确映射，不使用探索性的按时间截取结果作因果证据。
- r3：相同两组、单轮、30 次查询、四个挂载；只在 repeat 2～4 统计服务端所有现有线程及其后代的硬件计数，排除客户端。指令、周期等计数的 pcnt-running 均为 100%，没有 multiplex 缺口。计数窗口包括服务端 profile／交付尾部，不能与客户端 T 逐项直接相减。

下表均为三次预热后测量的完整 T 中位数，ms；每次均完成原 oracle 和完整输出验证。

| 诊断／轮 | GRIB S1 OFF→ON | HDF5 S2 OFF→ON |
| --- | ---: | ---: |
| r1／0 | 8.778→7.075 | 8.648→8.796 |
| r1／1 | 8.079→10.260 | 33.945→8.718 |
| r2／0 | 7.198→7.327 | 11.741→8.744 |
| r2／1 | 8.947→6.286 | 32.118→77.900 |
| r3／0 | 36.470→8.583 | 11.101→13.382 |

GRIB S1 原来的 ON 几倍慢化未稳定复现，r3 反而是 OFF 明显慢。HDF5 S2 的 ON 慢化在 r2／1 重现，但另一个 ON 挂载约 9 ms，OFF 也出现 32～34 ms 的慢化。r1 中另一 HDF5 S1 OFF 挂载达到 51.525 ms。它们不支持一个随 S 或缓存开关稳定变化的解释。

## 硬件计数：计算量与计时明显脱节

以下为 r3 每配置三次温热查询的**服务端窗口合计**，不是每查询均值。

| 组／配置 | 用户态指令，M | 用户态周期，M | 用户态 CPI | task-clock，ms | cache misses | context switches |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GRIB S1 OFF | 27.698302 | 40.767257 | 1.472 | 187.099 | 199,944 | 78 |
| GRIB S1 ON | 27.682164 | 32.040257 | 1.157 | 32.696 | 217,868 | 78 |
| HDF5 S2 OFF | 42.422738 | 44.061601 | 1.039 | 36.262 | 212,375 | 63 |
| HDF5 S2 ON | 42.391772 | 51.017664 | 1.203 | 39.571 | 206,474 | 63 |

两组 ON 的用户态指令分别只比 OFF 少 0.058%／0.073%。GRIB S1 OFF 的 cache misses 甚至更少，却出现 157.051 ms 单条查询；对应三条完整 T 是 157.051／36.470／26.301 ms，ON 为 22.760／8.583／8.280 ms。因此大幅差异不是新增块缓存造成的额外业务计算，也不是 ON 的 cache-miss 数激增。

157 ms 的 OFF 查询中，各登记 `server_total` 合计约 11.606 ms，残差约 145.445 ms。线程 envelope 的 daemon CPU 记账约 142.32 ms、runqueue wait 合计约 4.40 ms；粗粒度进程采样的用户／内核增量为 12／3 个 ticks（10 ms／tick）。它表明这次主要异常位于登记以外的共同交付／处理链路，普通来宾 runqueue 等待并不足以解释全部时间；同样不能把 CPU 记账直接当成新增计算。

实验机检测为 KVM、clocksource 为 `kvm-clock`。硬件指令进度近似不变，周期差异与 task-clock／墙钟倍数差异不相称，符合执行停顿或虚拟机 CPU 记账／PMU 口径差异的方向。**这是环境侧推断，不是已取得宿主抢占证据。** task-clock 含内核时间，表内 PMU 事件为用户态，虚拟 PMU 还存在环境限制，不能用二者直接相减计算“独占宿主停顿”。内核启动记录只确认使用 kvm-clock，没有发现时钟不稳定日志；本轮未获取宿主 vCPU 调度或 steal 的独立记录。

原始旧慢样本没有硬件指令记录，不能逐条追溯证明它们都由同一宿主事件造成。当前已排除的具体机制与仍未唯一确定的底层诱因，应保持这一边界。

## 处理结论和证据

不依据原来 7.675／5.080 这样的短样本比值回退块缓存，也不继续调整缓存容量来解释这些慢化。下一步应优先解决测量与环境隔离：记录宿主 vCPU 运行情况、使用可校验的统一时钟、把密集 artifact 哈希和全面资源审计移到配对测量块边界，并增加交错重复。每查询哈希与审计虽在 T 外，仍可能扰动后续查询；这是待单变量验证的观察者干扰，**本轮没有证明它就是根因**。

发现一个与本次异常无关的潜在效率点：`PayloadArtifacts.cpp` 在块缓存查找前预约整批 `4×bytes`，紧预算下可能先回收目标驻留，损失复用。这两条测量路径未触发它，未用其解释本轮慢化，也未在诊断中顺带修改实现。

本轮没有修改产品代码或重建产品。三轮共 210 次诊断查询（140 次 IoTDB-FS、70 次 FS-index）、28 个挂载，全部内容验证和独立保存证据审计通过。每轮均核验实际服务／资源恢复；最终原配置字节、ASYNC／true、DataNode 原亲和和 cgroup／controller 已恢复，28 个诊断挂载退出。产品沿用上一轮通过 2,115 单元测试和 22 配置检查的冻结构建；没有重复运行该全套测试。
