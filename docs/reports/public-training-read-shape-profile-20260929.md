# Electricity payload 读取：字节与范围成本剖析

2026-09-29，在 `root@192.168.99.49` 的独立 `public-arrow-baseline` 环境，对已发布且未修改的 Electricity Arrow 源版本 `1790670177863` 做只读测试。先增强训练查询 profile，再用与训练路径相同的 `IoTDBStructuredBlobBackend::read_payload_ranges` 接口执行两轴控制实验。这里的读取耗时包括 session 获取、`READ_OBJECT` SQL、数据返回、客户端转换与结果关闭；**不是 IoTDB 磁盘 I/O 或纯服务端执行时间**。

## 增强的 profile

`QueryRuntimeStats` 现在将每次实际 payload 调用同时归入范围数和请求字节数的 5×5 分桶。范围桶为 `≤1, ≤4, ≤16, ≤32, >32`，字节桶为 `≤16 KiB, ≤64 KiB, ≤256 KiB, ≤1 MiB, >1 MiB`；每格保存调用数、累计耗时、请求字节和范围数。JSONL 记录新增 `payload_read_shape`，原有总计不变。汇总器检查形状桶的调用数/耗时与总计相等，并排除同进程重叠请求。计时涵盖失败的实际读取尝试；仅 cache hit 不计入。

在新构建守护进程上执行两个相同的 370-channel、双窗口请求：首次请求有 **12 次 payload 调用、740 个范围、12,124,160 B、219.777 ms 读取耗时**，全部落在 `>32` 范围、`≤1 MiB` 字节桶，均值 **18.315 ms/调用**；第二次请求完全缓存命中，调用数和各桶均为零。两次记录都能与客户端不可变结果路径对应，汇总器接受 **2/2** 且没有重叠。这验证了新增指标在真实窗口路径上的记录与归因，不意味着训练全程都是同一桶。

## 随机交错的只读读形状实验

使用一个 IoTDB session，跳过一轮预热后，按固定随机种子在每轮交错执行 13 种形状，共 **50 轮、650 次**。固定字节组保持总量 1 MiB，改变 `READ_OBJECT` 范围数；分别测量相邻分片和间隔 64 KiB 的分散分片。再补齐 64 KiB × 1/64 范围，使这两个维度形成直接可比的 2×2 控制；固定 16 范围组扩展测量不同字节量。每个范围都在同一精确源版本内，逐次验证返回成功与列数。下表是每形状 50 次的均值：

| 形状 | 1 个范围 | 4 个范围 | 16 个范围 | 64 个范围 |
| --- | ---: | ---: | ---: | ---: |
| 1 MiB，相邻分片 | 11.14 ms | 11.31 ms | 12.66 ms | 17.09 ms |
| 1 MiB，分散分片 | 11.18 ms | 11.72 ms | 12.45 ms | 17.17 ms |
| 64 KiB，分散分片 | 4.12 ms | — | — | 10.68 ms |

以 **1 MiB × 64 范围** 的 17.17 ms 为参照，只把范围降至 1 个，配对均值节省 **5.99 ms**，50 轮 bootstrap 95% 区间 **[5.71, 6.30] ms**；只把字节降至 64 KiB、保持 64 范围，节省 **6.48 ms**，区间 **[5.84, 7.02] ms**。两个维度都有接近的边际成本。64 KiB 时，1→64 范围增加 **6.56 ms**；1 范围时，64 KiB→1 MiB 增加 **7.05 ms**。这组 2×2 实测没有支持“只由字节”或“只由范围”主导的结论。

相邻分片在 1 MiB 下由 1→64 范围也增加 **5.96 ms**；64 范围时，分散减相邻仅 **0.07 ms**，区间 **[-0.32, 0.46] ms**。在这个测试条件下，额外开销主要随请求列数增长，不能把它全部解释为物理跳读。具体耗时位于 SQL 解析、IoTDB 执行、RPC 或客户端结果构造的哪一步，现有边界仍不能确定。

| 固定 16 个分散范围 | 64 KiB | 256 KiB | 1 MiB | 4 MiB |
| --- | ---: | ---: | ---: | ---: |
| 平均每次读取 | 5.62 ms | 7.37 ms | 12.45 ms | 45.38 ms |

固定 **16 范围** 时，64 KiB → 1 MiB 的配对均值增量为 **6.82 ms**，区间 **[6.60, 7.05] ms**；64 KiB → 4 MiB 增加 **39.75 ms**，区间 **[38.74, 41.08] ms**。旧 50-step 训练的 571 次调用平均约 0.97 MB、52.8 范围、16.6 ms/调用，量级与这个探针及单个真实窗口的 18.3 ms/调用相符，但不同运行条件下不能按这些数直接推算训练提速。

## 对布局选择的意义和限制

128/256 元素 granule 可以降低字节量，却会增加 cache key、读取波次，并保留按通道分散的范围；需先扩容/改进缓存并实测调用形状。step-major 派生布局同时减少范围和调用，适合密集全通道视图，但有额外存储和版本刷新成本。当前实验只隔离了 **单次读取调用** 的字节/范围成本，未测重构后的训练墙钟、并行读波次、缓存驻留、SQL server CPU 或冷磁盘；两种布局都仍需要固定采样轨迹的端到端 A/B。
