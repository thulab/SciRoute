# V04 大文件有利场景实验

日期：2026-10-17（Asia/Shanghai）。状态：两次运行、独立审计与本地证据校验完成，原服务已恢复。

本轮测得的优势主要在空间：V8 相同内容的 payload 节省 87.5%；单点修改的 HDF5/GRIB 大文件节省 84.77%/76.45%。GRIB 4 MiB 档出现限定的温热查询收益，但相对 FS-scan 的 All 收益均只在四轮中的三轮成立，全部 **36 项四轮联合门禁均未通过**，没有证据据此将 V04 提升为通用查询性能主线。

## Material Passport

- 模式：run；类型：受控合成科学文件性能实验。
- 问题：放大单文件并提高跨版本块复用后，当前 V04 的完整查询耗时和存储账本能否优于 V03、FS-scan、FS-index？
- 用户授权：适当增加单文件规模，构造 V04 的有利场景以探索当前优势上限。
- 范围：既有原数据库、共用账号、相同许可证；冻结生产二进制，仅新增实验数据与工具。
- 推断边界：本配置下的有利场景结果，不是所有工作负载的理论上限；不据此自动切换开发主线。

## 配置与选择理由

N=8、K=2、D=4、depth=2，V=1/8。两格式、identical/single_unit、Latest/All，四系统 V04/V03/FS-scan/FS-index。64 个配置，4 个 campaign，每配置每轮 5 次，首请求单列，余下 16 个温热观测用于合并描述；时间重复单位是 4 轮；使用相同数据与主机，不宣称统计独立或显著性。

HDF5 每 dataset 为 `[1,1,1024,2048]` Float32（8 MiB），chunk `[1,1,256,256]`（256 KiB）、gzip level 1、不 shuffle，四个 dataset 全部真实分配。每文件 33,584,728 B，约 32.03 MiB。数值沿用原生成器的有限 Float32 随机位型，无填充或稀疏数据。

GRIB 为全球 0.25°、1440×721 网格，纬度 -90..90，经度 0..359.75，grid_simple/16 bit，四个 message 全部真实编码。每文件 8,306,636 B，约 7.92 MiB。全球网格使用新的实验生成函数，未更改旧小文件生成器。

All 在 V=8 命中 16 个单元，HDF5 输出 128 MiB Float32、GRIB 输出约 63.37 MiB Float32，另有 mask。这使数据处理成本显著高于原 4,096 元素的小单元，同时尽量使所选解码工作集容纳于沿用的 256 MiB runtime 缓存；不放大缓存容量。是否实际命中以原始 profile 为准。

源码复核进一步确认：GRIB 另有独立的 `GribDecodedFieldCache`，默认 64 MiB、最多 16 字段，保留 canonical Float64 及坐标轴；公共 256 MiB runtime 中的 GRIB 编码消息缓存与它不同。大网格 All 的 16 个原生字段仅 values 就约 126.74 MiB，不能全部容纳于 64 MiB。公共 runtime 的 hit/decode 计数不能直接当作原生字段缓存的命中／解码计数；本轮不改变生产二进制新增计数。

因此补充一个 GRIB 有利规模点：720×721，全球经度步长 0.5°、纬度 0.25°，其余 N/K/D/V、变更规则、预算和四对照不变。每文件 4,153,676 B（约 3.96 MiB），V=8 所选 16 个 Float64 字段与轴数组合计 66,631,808 B（63.5450 MiB），还剩 477,056 B 容纳 entry、路径与 logical fee trace。该估算支持有利规模的选择，不能替代实际命中证据，vector capacity 与 trace 开销也受缓存预算约束。内存预算保持不变。输入分块节省 identical 87.5%、single_unit 65.5333%，为较低块共享率与较有利解码缓存规模提供对照。

补充点位于 `work/grib-cachefit-upper-20261017/`，仅含 GRIB：32 配置、640 次正式查询、288 个科学发布、144 份 FS 副本、4 份 SQLite；独立新 namespace，主矩阵结束并恢复原服务后执行。该点的 namespace 不含 HDF5，因此跨规模比较同时包含目录组成差异，不称为纯缓存消融；每个规模内部的四系统对照分别报告。新单格式运行器的 9 项回归通过。

该补充点在主矩阵正式查询前，由冻结代码的缓存容量审查提出并生成，不依据最终查询数值筛选；较大的 GRIB 负结果也全部保留。“最优”只指本轮预定有利条件中的最好观测，不代表已搜索所有网格／选择性／缓存状态。

identical 引用同一输入，但在后端产生真实独立版本。single_unit 采用累积变更，槽位 `(ordinal-2)%4`：HDF5 只 XOR 选中 dataset 首个 Float32 的低尾数位；GRIB 只将一个非极值网格点加 1/128，并要求编码长度与所有 message 偏移保持不变。新 GRIB 变更粒度比旧 pilot 的整 message 重编码数值变换更小，因此与旧 pilot 的差异同时包含文件规模和变更模式，不能当作纯文件大小效应。

原始固定块账本显示，V=8 identical 的引用 payload 节省均为 87.5%；single_unit 的 HDF5 为 84.7681%，GRIB 为 76.4546%。这些首先来自输入字节分块，随后由实际后端 payload 图逐项确认，不等于物理磁盘压缩率。

逐版本比较真实文件的 1 MiB 块身份后，两格式各 56 次变更均恰好改变一个块，文件大小不变。HDF5 每文件有 33 块（含尾块），GRIB 有 8 块；因此相同的一个变化块，在较大的 HDF5 文件中占比更小。该性质来自实际科学编码，没有填充、稀疏文件或人为补齐块边界。

## 执行与验证协议

- 沿用 N8 的查询构造和完整计时边界。HDF5 按命中精确 path/version/dataset 分别 typed 读取；GRIB 每次合并匹配路径。所有历史结果保留独立 provenance，不按内容折叠输出。
- native 时钟覆盖版本选择、发现/SQLite、原生解码到 worker 内 owned arrays；IoTDB-FS 覆盖控制、发现、读取、IPC 和客户端 owned copy。哈希及 profile 等待排除；这不是相同传输边界的实验。
- 每 system/scenario/V 独立 namespace，共 8 个；两格式共用该 namespace，合计 576 次科学发布。Exact 空截断快照保留，格式筛选排除，不冒充数据版本。
- FS 使用 288 份独立普通文件，禁止硬链接、软链接和 reflink；每 scenario/V/format 一份完整历史 SQLite，共 8 份。索引构建、复制、摄取、恢复成本在查询时钟外单列。
- 每个 scenario/V 的系统顺序采用四轮循环排列，每组系统恰好占据每个顺序位置一次。不是完整随机化，也不能消除所有顺序与系统状态影响。
- 新 owner/worker 每轮重新启动；仅首轮恢复后核验全部历史文件 SHA 和未过滤科学目录（主矩阵 576 个科学版本／2304 个目录单元，补充点 288／1152），后续轮保留恢复身份检查而不重复整历史扫描。每次实际查询的目标值/mask/精确版本均对照独立原生 oracle；未命中的全部目录单元不冒称都单独 typed 读取。准备会暖 OS 页，不宣称冷盘。
- 主指标为完整查询耗时 T；同时计算 Δ=T8−T1、G=T8/T1、S=T_control/T_V04、R=S8/S1。联合通过要求四轮分别同时满足完整耗时更低、增量更小和 R>1。

新增 8 项实验回归通过：单点数值变化、GRIB 偏移不变、固定块尾段、完整配置计数、缺失/重复/未验证观测拒绝、首请求排除、端点比值和联合门禁、四轮位置平衡，以及拒绝部分发布或已有查询记录的准备续接。

## 结果

两次运行合计 **1,920 条完整查询、96 配置、864 个科学版本、432 份 FS 独立副本**，原始记录与实际 payload 图均通过独立审计。主矩阵四轮联合门禁为 **0/24**，GRIB 补充点为 **0/12**。主矩阵 V=8 的全部 8 个温热合并单元，V04 均慢于 V03 和两类 FS。

补充的 GRIB 4 MiB 档：single_unit/All 的 V04/V03/FS-scan/FS-index 为 **388.462/413.695/419.902/126.473 ms**；V04 对 FS-scan 的合并速度比 1.081，版本绝对增量 324.351 ms，低于 FS-scan 的 365.872 ms，R=1.283。但四轮速度比分别为 1.084/1.110/1.129/0.954，联合只通过 3/4。identical/All 对 FS-scan 合并速度比 1.017，也只通过 3/4。不能把合并中位数的弱收益改写为稳定通过。

single_unit/Latest 对 V03 的 V8 完整耗时为 51.334/60.950 ms，合并速度比 1.187，四轮绝对耗时均更低；包含增量和 R 的联合门禁仅通过 2/4。保留这一局部绝对收益，同时不将其归因为已证明的 payload 共享收益。所有规模的 FS-index 对照均更快，未出现 V8 campaign 级完整耗时优势。当前结论继续保留 V03 作为查询性能参照，V04 作为内容共享与限定工作负载候选，不自动推进 V05/V06。

主矩阵 HDF5-All identical 的 V04/V03/FS-scan/FS-index 完整耗时为 1552.068/1401.035/384.825/352.912 ms；single_unit 为 1477.653/1385.942/380.463/363.152 ms。V04 两单元都记录 512 个公共 runtime 缓存命中，0 payload 读取、0 decode、0 解压，查询内两条 SDK 路径均 0 SQL 提交；并非仍在为所有历史文件做 payload 读取。

增长倍数与成本必须一起判断。例如主矩阵 identical/HDF5-All，V04 的 G=8.448，低于 FS-index 的 11.474，但 V04 的 V1 为 183.709 ms，FS-index 为 30.758 ms；绝对增量分别为 1368.358/322.154 ms。不能把更高基线带来的较小倍数称为跨版本查询优势。

V04 identical/HDF5-All 的 profile 中位数：取值客户端 1538.095 ms、取值服务端 1090.718 ms、typed IPC encode 528.848 ms，其中 array build 409.676 ms；IPC 为 135,291,136 B（约 129 MiB）。这些是分别计算的中位数，阶段存在包含关系，不相加或用差值重建完整请求。结果表明数组构建、IPC 与客户端拷贝是当前大输出路径的重要成本；它们不能由底层块共享率消除，也不能据此把全部 V04/V03 差异归因于单个阶段。

GRIB decoded-field 缓存按 namespace、path、version、revision、message offset/length 区分，相同字节的不同版本仍有独立 entry。当前 payload 内容共享没有自动变成跨版本解码结果合并。无原生字段缓存 hit/miss 直接计数时，公共 runtime 的 0 decode 不能证明 ecCodes 无解码或字段全部常驻。

补充点 V04-All 的取值 IPC 均为 33,412,568 B；identical/single_unit 的 typed cursor execute 中位数约 33.906/31.948 ms，IPC encode 为 152.416/161.862 ms，公共 runtime 的 payload 读取与解码计数中位数为 0。较大 GRIB 档到此档还同时改变网格、输出字节及 namespace 组成，这些数值与缓存适配假说一致，但不能单独证明原生 field-cache 命中率或纯缓存因果效应。V03 也有同类缓存，不能把与 FS 的差异全部归因于 V04 去重。

主矩阵两格式合计，V1 的唯一 payload 为 335,130,912 B，全部 objects 为 335,916,926 B。V8 identical 的唯一 payload 仍为 335,130,912 B，objects 为 344,350,924 B：相较 V1，objects 只增加 8,433,998 B（2.51%）；V8 single_unit 唯一 payload 为 452,571,424 B，objects 为 462,062,364 B，objects 增加 126,145,438 B（37.55%）。两场景的完整科学文件逻辑字节均由 335,130,912 B 增至 2,681,047,296 B（8 倍）。这是当前版本共享的明确空间收益。

objects 包含保留的 COW 历史与不可达对象，但不是 whole-backend：未计 head／secondary／staging 表、WAL、TsFile 与数据库编码开销。V03 的独立 payload 也不在其 objects 账本中。因此不能据此计算数据库物理压缩率，或把 V03 objects 与 V04 objects 当作两系统总占用直接比较；FS 的实际分配字节另列。所有 V04 namespace 的 staging payload 行为 0，当前 head 前后摘要一致，未执行 GC。
